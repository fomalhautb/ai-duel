# AI Duel 架构说明

## 1. 项目边界

这是一个黑客松项目，目标是**在有限时间内做出一个能上手玩、能演示的 1v1 卡牌对战**。
架构上的每一处取舍都服从这个目标，下面这些是**明确不做**的：

- **不做服务器权威**：服务端不跑规则、不存对局状态，改客户端就能作弊。
- **不做防作弊**：同上，双方看得见彼此的手牌也无所谓（见 4.3）。
- **不做匹配系统**：只有"建房 / 输房间码进房"，没有排队、没有段位、没有大厅。
- **不做账号**：存档只有浏览器 localStorage（卡牌收藏、胜场、牌组、英雄、教程标记），
  换个浏览器就是新号。
- **不存对局**：刷新页面 = 这局没了，只有收藏和胜场留得下来。
- **不做向后兼容**：协议、卡牌数据、状态结构随时可以推倒重来，不留迁移层。
- **不做主机 / 手柄**：只认指针设备（鼠标和手指），没有方向键在界面里跳来跳去那一套。
- **不做竖屏版式**：全站是一整块 16:9 的死版式（见下），竖屏塞不下，直接请玩家转横屏。

需求变化时优先砍功能，而不是加抽象层。

### 1.1 触屏一定要支持

**手机横屏必须能正常玩**，触屏和鼠标是同等的一等公民。

底线是"两种设备尽量走同一套代码"：分叉一处，在电脑上验过的行为就少代表一分手机上会发生什么。
真需要分开的地方一律按**这次事件的 `pointerType`** 判，而不是按设备类型——
带触屏的笔记本用鼠标操作时走的仍然是鼠标那条。全项目的分叉点只有下面这几处，
每一处的理由都写在实现旁边：

- **版式不为触屏另做**。每一页都是 1672×941 的舞台按视口等比缩放（做法和理由写在
  `styles.css` 的「对局界面的 16:9 舞台」一节，其余几页同款），
  横屏下手机和电脑看到的是同一张画面，只是小一号。
  竖屏则由 `ui/OrientationNotice.tsx` 盖一层「请横屏」，不做第二套版式。
  舞台高度用 `100dvh` 不用 `100vh`：手机浏览器的 `vh` 是地址栏收起时的高度，
  用它算会把手牌那一截切到屏幕外。
- **出牌两条路：拖进战场松手，或者原地轻点。轻点的后果按输入设备分**（见 5.6）——
  鼠标点一下就打出；触屏点一下只是把牌**选中**，牌抬起放大、顶上冒出一颗「打出」，
  再点那颗才真的打出。手指划过屏幕太容易蹭出一次点击，而出牌不可撤销，所以触屏多一步确认；
  鼠标点哪儿是哪儿，多这一步只是拖慢节奏。
- **拖拽时牌抬到手指上方**（`HandFan` 的 `TOUCH_DRAG_LIFT`），不然卡面全被指头盖住。
- **浏览器的默认触屏手势要一条条关掉**：`touch-action` 关滚动和双击放大（不关的话手指一动
  就被当成滚页面，拖拽连 `pointermove` 都收不到）、`overscroll-behavior` 关下拉刷新、
  `-webkit-touch-callout` 关长按菜单（长按恰好是抓牌的动作）。这几条集中在 `styles.css`
  开头那一段，加上被拖元素各自的 `touch-action`。
- **只有悬停才出现的东西必须另有出路**：卡面倾斜和高光在触屏上整个关掉（`ui/cardTilt.ts`）；
  手牌和卡池右上角的问号（只有技能牌有，见 5.7）都从"移入翻面"换成"点一下翻一次"；
  那个问号连同牌组格子上的「×」在粗指针下常驻显示——它们原本只在 hover 时才露出来，触屏永远等不到，
  于是背面再也看不到、加进牌组的牌也再拿不出来。
  一律不留"按住才看得见、一松手就没"的半吊子行为——触屏的 `pointerenter` / `pointerleave`
  其实是按下和抬手，照着 hover 抄必然是这个下场。
- **点击区在粗指针下放大**（`@media (pointer: coarse)`）：舞台按视口缩放之后，
  照鼠标精度定的 20~28px 小控件在手机上只剩一半大，指尖按不中。
  卡组页那两颗圆钮（卡池的「＋」、格子的「送回」）不在此列：它们本身已经是 52 / 40px，
  和左下角的份数圆章成对，触屏档只改显隐、不再另摆一套落位和尺寸。

## 2. 三个包

TypeScript + pnpm monorepo，三个包互不循环依赖：

```
packages/
  core     @ai-duel/core     纯规则引擎（无渲染、无 IO、无网络）
  client   @ai-duel/client   Vite + React + GSAP（全部是 DOM，没有画布）
  server   @ai-duel/server   Cloudflare Worker：消息转发器 + 前端静态资源托管
```

依赖方向只有一条：`client → core`。
`server` 不依赖 `core`——它根本不需要知道游戏是什么。

三个包都**不经过 tsc 编译产出 JS**：`client` 交给 Vite，`server` 交给 wrangler（它自己打包上传 Worker），
`core` 的 `exports` 直接指向 `src/index.ts`，被前两者当源码消费。
`tsc` 在这个仓库里只当类型检查器（`pnpm typecheck`）。少一个构建步骤，改 core 立刻生效。

## 3. core：确定性状态机

### 3.1 唯一的接口形状

```ts
createGame(setup): { state, events }        // 开局：洗牌、发起始手牌
execute(state, command): { state, events }  // 执行一条指令
```

**指令进，事件出。** 这条约定是整个架构的地基：

- `execute` 是纯函数，不改传入的 `state`，返回全新的状态。
- 同样的 `state` + 同样的 `command`，永远得到同样的结果（没有 `Math.random`、没有 `Date.now`）。
- 开局那一串随机在 `createGame` 里一次掷完（抛硬币定先手、洗双方牌组、洗题序），靠 `seed` 固定。
  洗完之后抽牌就是从牌堆末尾取、题目按洗好的顺序逐轮取，都不再需要随机。
- `execute` 里只有「内存紧缺」一张牌要掷随机，用的是状态里的 `GameState.rngSeed`：
  `mersenne(rngSeed)` 起一把生成器，取完值再把下一颗种子写回状态。
  生成器本身不可 JSON 序列化，进不了状态，种子可以——这样上面那条"同样的状态 + 同样的指令
  = 同样的结果"仍然成立，房主广播完快照，客人手上的种子和房主是同一个。
- `GameState` 必须全程可 JSON 序列化（引擎内部就是用 JSON 深拷贝推进状态的）。
  别往里塞函数、`Map`、`Date`。

### 3.2 事件流是给客户端播动画用的

`events` 描述"**已经发生的事实**"，例如一轮打完是这样一串：

```
ROUND_STARTED → PLAY_TURN_STARTED → AI_DEPLOYED → SKILL_PLAYED → SKILL_CANCELED
  → PLAY_TURN_STARTED → QUESTION_REVEALED → AI_ANSWERED × N → AI_ELIMINATED
  → ROUND_SCORED → GAME_OVER
```

`SKILL_CANCELED` 只在英雄技能抵消了那张技能牌时才有，紧跟在它的 `SKILL_PLAYED` 后面
（`player` 是出牌方，`by` 是发动技能的英雄持有方，两个方向相反，别弄混）。
主动英雄技能则发一条 `HERO_SKILL_USED`（升降级，见 3.4），可以插在出牌轮里的任何位置。

技能牌的效果事件同样跟在自己那条 `SKILL_PLAYED` 后面（客户端先演牌打出去，再演它造成了什么）：
`AI_REMOVED`（被「内存紧缺」/「国产替代」罚下，`by` 说明是哪张牌干的）、
`AI_TRANSFORMED`（被「鸡犬升天」换成进化链的下一张）、
`CARD_REMOVED`（被「模型蒸馏」弃掉的那张手牌 AI）。被抵消时这些一条都不会有。
答题结算里还有一条 `AI_SAFE_PASSED`：答错了但因为「保送」留在场上，
占的就是本该发 `AI_ELIMINATED` 的位置。

`ROUND_SCORED` 除了 `gains` / `scores`，还带着判定的**全部依据**：`correctCounts`（双方本轮
答对的 AI 数量）、`spent`（双方本轮消耗）、`verdict`（`'more-correct'` /
`'fewer-tokens'` / `'equal-tokens'`，见 3.4 的三条判定）。带全是有原因的：
`correctCounts` 不能拿结算后场上人数代替：被「保送」的单位答错也留在场上。
客户端的结算文案和教程的提示语都直接读它。

客户端拿到这串事件后逐条播动画（卡牌飞出去、硬币转起来、题目全屏揭晓、比分跳动），
**不重新计算规则**。这样做的好处：

- 动画节奏和规则解耦：想让某个效果播 0.5 秒还是 2 秒，只改客户端。
- 联机时只需要传事件流，另一端播出来的画面和房主一模一样。

### 3.3 非法指令

指令不合法（还没轮到你出牌、现在不是出牌阶段、手牌里没有这张卡……）时，
`execute` 返回**原样的 state** 加一条 `COMMAND_REJECTED` 事件，不抛异常。
调用方可以选择把它显示成提示，也可以直接忽略。

### 3.4 数据模型要点

**一局怎么走。** 开局抛硬币定第一轮先手，之后每轮交换。一轮分四段：
`phase: 'play'` 双方轮流出牌（先手打完点「结束出牌」轮到后手，后手再点就进答题），
`phase: 'quiz'` 全场 AI 一起答题、答完当场计分，
`phase: 'settle'` 分已经写进快照，停在这儿等双方各确认一次。
两边都确认了才推进下一轮；到那一刻若有一方单独拿到 `WIN_TARGET`（3）分、
或者题库已经出完，那次确认就把 `phase` 变 `'finished'` 而不是开下一轮。

**`settle` 单独占一段**，是为了给结算界面留一段"局面不再变"的时间：分算完了，
但轮次、Token、手牌还全停在本轮的样子，界面可以放心读快照
（"本轮消耗"这种数只在这一刻有意义）。补牌、换先手、Token 补满一律推迟到双方确认之后。
**推进要等两边**则是另一回事：结算界面是一整套逐步揭晓的动画，两端各播各的、快慢不同步，
先看完的一方直接把局面推走的话，另一边的动画会被下一轮的横幅和补牌打断。

- `round` 从 1 开始，`totalRounds = questions.length`。它是**上限**而不是"这局要打几轮"：
  正常先到 3 分就收场，打满只发生在双方一路同分加赛的情况下。
- `firstPlayer` 是本轮先手，`activePlayer` 是当下轮到谁出牌。
  **不另设"先手是否已结束出牌"的标志位**：`activePlayer === firstPlayer` 就是先手在出，
  否则就是后手在出，后手再 `END_PLAY` 就进答题。少一个字段就少一处可能对不上的状态。
- `questions` 是本局洗好的题序，`questions[round - 1]` 是本轮的题。
  每道题仍保留 `keywords` 元数据；当前对战界面不展示，只在「下一题」牌匾里显示题目类别。
  **整份题库连正确答案一起放在 `GameState` 里发给双方**，不做"只在结算时下发"这种
  服务器权威式的遮挡——本项目不防作弊（见 4.1），界面自己决定什么时候揭晓。
- `settleConfirmed` 按座位号记 settle 期间两人确认过没有，每次进 settle 重置成 `[false, false]`。
  玩家点「进入下一轮」发的是 `CONFIRM_ROUND`，引擎回一条 `ROUND_CONFIRMED`；
  同一个人重复发会被拒（所以界面按下之后要把按钮置灰等对方），两条齐了才推进或结束整局。
- `winner` 可以是座位号、`'draw'` 或 `null`（还没打完）。
  平局是正经结果之一，但只可能出自"题库出完了双方还同分"这一条保底路径。

**每轮怎么计分（机制文档 V0.3 §2 / §9）。** 一轮只产生 1 分，按三条依次判
（判据一律取自提交上来的 `AnswerResult`，不是罚完之后场上还剩几个——被「保送」的单位
答错也留场，照场上还有没有人来判会把它算成答对）：

1. **答对 AI 数量不同** → 数量更多的一方 +1。场上没有 AI 的一方答对数为 0。
2. **答对数量相同** → 比 `PlayerState.spentThisRound`（本轮为新打出的牌
   花掉的 Token），严格少的一方 +1。老 AI 留场不重复计费，所以"什么都不打"是消耗 0 的合法打法。
3. **消耗也相同** → 双方各 +1。正因为有这一档，才会出现"双方同时到 3 分"。

计分在 `quiz` 末尾就算完并写进快照，但**收场判定押后到双方确认**：
到那一刻一方分数 ≥ 3 且双方分数不相等就结束（题库还剩题也不打了）；
同时到线且分数相同则继续加赛；题库出完仍未分出时保底比总分，相同才是 `'draw'`。

算完发一条 `ROUND_SCORED`，成对的字段都按座位号排：`gains` 是本轮各自拿到的分
（只可能是 0 或 1，答对数和消耗都相同时是 `[1, 1]`），`scores` 是加完之后的总分，
`correctCounts`（答对数量）/ `spent` / `verdict` 是上面那三条判据本身。
判据跟着一起发，界面才讲得清"凭什么这一分给了谁"，客户端不该自己再算一遍。

**卡牌和单位。** 全系统只有三类牌，靠 `kind` 区分，其中前两类进牌组：

- `AiCard`（`kind: 'ai'`）打出后作为 `AiInstance` **留在场上跨轮答题**，
  答错才罚下进弃牌堆。它的 `model` 字段（GPT / Claude / …）只印在卡面上，引擎不读。
- `SkillCard`（`kind: 'skill'`）打出后直接进弃牌堆。24 张里 10 张接了引擎、14 张还只有卡面
  和亮相动画（名单见 `core/src/skillCards.ts` 的文件头注释，还没实装的带着 `plannedEffect`）。
  卡面标了 `target` 的要在打出时指定目标，共四档：
  `'foe-ai'`（对方场上一个 `interference` 没设置的 AI）、`'own-ai'`（己方场上没被保送的）、
  `'own-affected-ai'`（己方场上带着 `interference` 的）、
  `'own-hand-ai'`（**自己手牌里**的一张 AI 牌，「模型蒸馏」用，`targetInstanceId` 指的是手牌实例）。
  该填不填、目标不在该在的地方、或者目标不符合那一档的条件，都会被 `COMMAND_REJECTED` 挡回去，
  理由是能直接给玩家看的中文；没有 `target` 的卡带上 `targetInstanceId` 则直接忽略。
  效果按 `card.id` 分派（`engine.ts` 的 `applySkillEffect`），一律写在
  "没被英雄技能抵消"的那条分支里。
- `HeroCard`（`kind: 'hero'`）是开局前选的英雄牌，每方一张，**不进牌组也不进手牌**：
  它不在 `HandCard` 联合里，也不在 `CARDS` / `CARD_POOL` / `STARTER_DECK` 里，
  单独一张表 `src/heroes.ts`（`HEROES` + `getHero`）。
  英雄技能不占 20 张牌的牌组空间（见游戏机制文档第 4 节），塞进卡池还会连累存档过滤、
  抽卡和洗牌——那几处都是"遍历卡池"的写法，多出一张抽不到也打不出的卡只会变成脏数据。

所以 `HandCard = AiCard | SkillCard` 才是牌组、手牌、弃牌堆里实际会出现的类型，
`CARDS` / `getCard` 也只收这两类；`Card = HandCard | HeroCard` 只给"泛指一张卡"的展示代码用
（卡面渲染、牌组页、背面文案）。

**Token。** 进牌组的两类牌都有 `tokenCost`（AI 牌 1~7、技能牌 1~10），
`PlayerState` 上一对 `tokens` / `tokenMax` 记这一轮的剩余和上限：
开局各 `INITIAL_TOKEN_MAX`（5 点），双方确认结算、真的进下一轮时
`tokenMax += TOKEN_MAX_GROWTH`（1 点）并把 `tokens` 补满——**省下来的不跨轮累积**，
直接被新的满额盖掉。
涨得慢是有意的：一局最短三轮就结束，涨太快的话最后一轮想买什么买什么，
「答对数量相同时比本轮消耗」那条决胜线就没有分量了。
`playCard` 里费用那道闸排在选目标之前：不然客户端会让玩家挑完目标才被告知打不起。
`HeroCard` 没有这个字段，它不进牌组也就不用出。

`tokenCost` 是卡面上印的**原价**，真正扣多少要过一遍
`effectivePlayCost(state, card)`：「核电站」每打出一张就让双方后续的牌便宜 1 点
（计数在 `GameState.costReduction`，可叠加、最低减到 1 点、进下一轮清零）。
减费对谁都一样，金钟罩也挡不住它：罩子挡的是落在场上单位身上的效果，
而减费改的是"这张牌打出去要花多少"（见下）。
这个函数是 core 导出的：客户端的"打不起就变灰"必须和引擎的扣费校验用同一个数，
各算一遍就会出现"看着能打、点下去说 Token 不够"。
`tokens -=` 和 `spentThisRound +=` 记的也都是这个实际费用。
唯一一处按原价算的是「模型蒸馏」换来的 Token（就是被弃那张的印刷费用）：
核电站减的是"打出去要花多少"，不该连带把回收价也压下去。
它换来的 Token 允许顶破 `tokenMax`，多出来的部分在下一轮补满时被覆盖。

**「本轮」效果和它们的清除点。** 技能牌留下的标记都只活一轮，
统一在 `confirmRound` 里真的进下一轮那一步清掉：`GameState.costReduction` 清零、
双方的 `PlayerState.shielded` 删掉、场上每个单位的 `interference` / `safePassed` 删掉。
清除点定在这里而不是提交答题结果时，是因为结算界面还要照着这些标记演一遍
"这个被干扰了 / 这个是被保送留下的"。

「金钟罩」挡的是**落在场上单位身上的技能牌效果**：`shielded` 期间，任何技能牌
（无论谁打的）都不作用于这一方和他的 Agent——对方的干扰牌选不中他的 AI
（选目标那一步直接拒绝）、他自己也打不出「玉净瓶」「保送」这类只作用于自己场上单位的牌、
群体牌结算时跳过他的场面。对己方有利的效果一起挡是有意的，卡面就是这么写的。
够不着场上单位的东西它管不着：「核电站」减的是出牌费用，罩着照样享受；
「模型蒸馏」弃的是手牌，罩着照样能打。
金钟罩自己也不受自己影响，否则第一张就会把自己挡住、这张牌永远打不出去
（第二张则被"本轮已经有金钟罩了"拒掉）。
英雄技能不是技能牌，格蕾丝·霍珀的 Debug 照常能抵消金钟罩本身。

另有一份 `spentThisRound` 记这一轮**花出去了多少**，它是 Token 决胜的依据。
不拿 `tokenMax - tokens` 现算：那个差值在出牌阶段数值相同，但表达的是"额度剩多少"，
一旦出现「回复 Token」这类效果（「模型蒸馏」已经是一例）就不再等于消耗；
何况进下一轮时 `tokens` 会被补满、`tokenMax` 还要涨，差值当场就没了，
而结算界面上那行「本轮消耗」正需要在那之前拿到它。
清零也因此排在真正进下一轮那一步（双方确认之后），不在提交答题结果时。
技能牌被英雄技能抵消也照样计入——Token 是真花出去的，作废的只是效果。

**每轮出几张牌只由费用管**：AI 牌和技能牌都不限张数，Token 够就能接着打，
不够的那张在 `playCard` 里直接 `COMMAND_REJECTED`。`DEBUG_PLAY_CARD` 走同一个 `playCard`，
所以同样受费用约束——调试只豁免"轮到谁出牌"那一条（见 3.6）。

**英雄。** `PlayerState.hero`（`HeroId | null`）是这一方选的英雄牌，
`PlayerState.heroSkillUsed` 记这一局有没有发动过。开局由 `PlayerSetup.hero` 指定，
不填就是默认英雄（格蕾丝·霍珀）。两条开局路径都会把玩家挑的那位传进来：
匹配房里双方各走一遍选英雄页，客人把结果随 `match:loadout` 发给房主，房主凑齐两份才建局
（见 `screens/RoomScreen.tsx` 的 `tryStart`）；dev 测试房只有一个真人，我方读本地存档里存着的那位，
对面座位不填、用默认的霍珀。
"每局一次"的一局就是一个 `GameState` 的生命周期，`createGame` 重新建状态时标志天然回到 false。
英雄初始化不消耗随机数，不影响 `createGame` 里那串随机数的顺序（见本节末尾）。

人物名单 7 位全部在 `HEROES` 里（`src/heroes.ts`），文案都定了案，但实装的只有 4 位；
另外 3 位（李飞飞、米拉·穆拉蒂、玛格丽特·汉密尔顿）标着 `comingSoon`，
选英雄界面要把她们置灰禁选，别让玩家选完才发现技能不生效。已实装的四位分两类：

**被动，引擎自己算：**

- **格蕾丝·霍珀 · Debug**——每局抵消对方打出的第一张技能牌的效果。
  判定就在 `playCard` 的技能牌分支里：牌照常进弃牌堆、照常发 `SKILL_PLAYED`，
  如果对手 `hero === 'grace-hopper'` 且技能没用过，就把标志置上并追发一条 `SKILL_CANCELED`
  （顺序不能反，客户端要先演牌再演抵消）。
  **"会不会被抵消"必须先算、效果写在"没被抵消"的那条分支里**：
  `applySkillEffect` 整个只在 `canceledBy === null` 时才被调用，被抵消时一个标记都不留，
  否则会出现"技能被抵消了，那个 AI 却再也不能被干扰"的自相矛盾局面。
  新技能牌加效果时照这个位置写，否则 Debug 只剩一层动画。
  被抵消的那次出牌事件里仍然带着 `targetInstanceId`：牌确实是冲着那个 AI 打出去的，
  客户端先演飞过去、再演抵消，玩家才看得懂这一下本来要打谁。
  `DEBUG_PLAY_CARD` 走的是同一个 `playCard`，抵消是顺带覆盖到的。
- **阿达·洛芙莱斯 · 第一算法**——整局每一轮的 Token 上限额外 +2。
  只在 `createGame` 的 `makePlayer` 里把起点抬高 `ADA_TOKEN_MAX_BONUS`（开局 7/7），
  之后 `confirmRound` 走的是 `tokenMax += TOKEN_MAX_GROWTH` 的增量逻辑，
  这个 +2 会自然贯穿整局（第 2 轮 8、第 3 轮 9……恒比对手多 2）。
  一局最短 3 轮就结束（先到 3 分），所以这 +2 差不多等于白送一张中费 AI 牌。
  这是**有意的"全程上限 +2"**，不是只加第一轮。它是开局就算进数值的被动，不占 `heroSkillUsed`。

**主动，玩家发 `USE_HERO_SKILL { player, targetInstanceId }`：**

- **陈丹琦 · 精准检索**——每局一次，指定 1 个**己方**场上单位升为同系列下一代。
- **梅拉妮·珀金斯 · 化繁为简**——每局一次，指定 1 个**对方**场上单位降为同系列上一代。

两位共用 `useHeroSkill`：升还是降、目标该在哪一侧全由英雄决定，指令本身不带方向。
校验和出牌同一道门槛（`phase === 'play'` 且轮到自己），但**完全免费**——不扣 Token、
不记 `spentThisRound`（所以不影响"答对数量相同时比消耗"那条决胜线，见本节开头的计分）、
更不结束出牌轮，发动完照样接着出牌。
英雄不对、技能用过了、目标不在该在的那一侧、目标已经到链顶/链底，都回 `COMMAND_REJECTED`。
效果就是把那个单位的 `cardId` 换成升级链上相邻的一张（`AI_UPGRADE_CHAINS` / `upgradeTargetOf` /
`downgradeTargetOf`，在 `src/aiModels.ts`），然后发一条 `HERO_SKILL_USED`（带前后两张卡的 id）。
**能力变化全靠"换成了另一张卡"**：费用、卡面、预生成的答题表现本来就按 `cardId` 查，
换完自然换了一整套答案，引擎不必再理解"强了多少"。
（降到链底可能降出 GPT-2 这种"调不到模型、没跑过预生成"的卡，那时 `scriptedAnswers`
给一句固定的"答不出来"并判错，不会缺格抛错。）
链只覆盖真有代际关系的四个系列（GPT / Claude / DeepSeek / Kimi），其余 8 张升不了也降不了。
被干扰过、被保送过的单位照样能升降级，几个标记各管各的、互不覆盖：
升完照样只会答「香蕉」，也照样答错不罚下。
「金钟罩」也管不着这里——它字面全挡的是**技能牌**，而英雄技能不是技能牌。
链**不避开**「调不到模型」的那两张（见 `UNAVAILABLE_AI_CARD_IDS`）：GPT-2 是 GPT 链的链底，
珀金斯照样能把对面的 GPT-3.5 降成它。那份名单管的是"能不能选进牌组"，
而答题眼下走 `script.ts` 的静态表、18 张卡全有词条，降成 GPT-2 一样答得出来；
不特判是有意的，多一条"跳过调不到的那张"只会让"降一代"变得难以预期。

`Card` 是卡牌**定义**（同一张卡在牌组里可以有多份），`CardInstance` / `AiInstance` 是
**实例**，带独立的 `instanceId`。AI 牌上场时沿用手牌那一份 `instanceId`，罚下时才能原样塞回
弃牌堆。`AiInstance` 除了身份三件套（`instanceId` / `cardId` / `owner`）还有四个可选字段，
分两类，别混：

**三个「本轮」标记**，进下一轮时一起清掉（`confirmRound`）：

- `affectedBy`：本轮打在这个单位身上的技能牌，按命中先后排。**只给界面用**，引擎的判定
  一概不读它：小卡上每一项挂一枚角标、放大查看时列出牌名（见 5.5）。凡是效果落在某个
  场上单位身上的技能牌，结算时都要往这里补一笔，不然那张牌打出去战场上不留痕迹；
  效果被移除时对应那一项也要跟着删（眼下只有「玉净瓶」解干扰这一处），
  所以它是"现在身上有什么"而不是一本流水账。引擎里统一走 `markAffected` / `unmarkAffected`。
  「金钟罩」不记在这里——它罩的是整个人，连本轮之后才上场的单位一起罩着（见 `shielded`）。
- `interference`：被哪张干扰牌命中了（`'fixed-answer'` 或 `'black-white-reversal'`）。
  记种类而不是一个布尔，是因为下游要分两处用：答案生成层按种类改写回答（见 4.5）、
  「玉净瓶」按"身上有没有它"挑目标。一个单位同时只挂得住一种。
- `safePassed`：被「保送」选中过，本轮答错也不罚下，改发 `AI_SAFE_PASSED`。
  它只免掉罚下，**不改计分**：被保送留场的那个仍然算答错。

后两个和 `affectedBy` 有重叠是有意的：它俩是引擎自己要读的机制，那一份只管展示，两边一起写。

**一个跟着单位走的标记**，不按轮清：

- `levelShift`：净升降级次数（升 +1 降 -1），**纯粹给界面画角标用**，引擎不读它。
  英雄技能每局只发得动一次，换掉的卡面身份也是永久的，所以它跟着单位走到下场为止。
  英雄技能不进 `affectedBy`（那一份只记技能牌），留下的就是这个数。

四个都写成可选字段、只设不为空的那一档，没被打过的单位就不带这一项，
JSON 深拷贝和联机转发都少一份冗余（`PlayerState.shielded` 同一套写法）。
`AiCard` 那边另有两个给技能牌读的标签：`domestic`（国产，「国产替代」按它清场）和
`evolvesTo`（同系列的下一代，「鸡犬升天」顺着它换卡面；不填就是不可进化）。
**`evolvesTo` 也是升降级链的唯一出处**：`AI_UPGRADE_CHAINS` 是顺着它现串出来的，
不另写一份名单，免得「鸡犬升天」和英雄技能对同一张卡给出不同的下一代。
哪天有了"上场后被增益/削弱"的数值，再把卡面数值拷贝一份到实例上。

**题库和答题结果。** `src/questions.ts` 是题库（`QUESTION_POOL`），每道题带类别
（`meme` 梗题 / `bias` 刻板印象 / `life` 生活类）、题面、正确答案 `answer`
和一句 `explanation`。答案和说明拆成两个字段是排版逼出来的：结算界面把 `answer` 当大字标题排，
写成整句会挤成两三行，"为什么是这个答案"归 `explanation` 那行小字。
`src/script.ts` 的 `scriptedAnswers(question, aiUnits)` 查的是 `src/pregenAnswers.json`：
一张「题目 × AI 牌 × 干扰变体 → 对错 + 回答 + 理由」的静态表，纯函数、确定性。
表里装的是**真实模型回答**——离线用 OpenRouter 跑完存下来的（生成 `scripts/pregen-answers.mjs`、
判卷 `scripts/judge-answers.mjs`、合成 `scripts/build-core-answers.mjs`），
所以对局里不联网也不会失败。变体那一维对应场上那个 AI 被哪张干扰牌打中（见 `AiInstance.interference`）。
它不是引擎的一部分：答题结果由 `SUBMIT_ANSWERS` 指令从外面喂进来（为什么这么分见 4.5）。
一条 `AnswerResult` 是 `{ instanceId, correct, answer, reasoning }`，
`answer` 同样是短语、`reasoning` 是两行以内的理由，正好对上结算卡里那一大一小两行。
引擎照它发出的 `AI_ANSWERED` 还额外带一个 `cardId`：答错的 AI 紧接着就被罚下，
界面收到事件时新快照还没提交，等提交完那个单位已经从场上消失，回头查不到它是哪张卡。

**随机**（开局那一串在 `createGame` 里，对局中只有「内存紧缺」一处，见 3.1），三处细节值得记一笔：

- 用 `pure-rand` 的 **`mersenne` 而不是更快的 `xoroshiro128plus`**。后者从整数种子起步时，
  相邻种子头几个输出的低位强相关（实测连续种子掷硬币约 65% 概率翻面，空转多少次都甩不掉），
  而这里的 `seed` 就是 `Date.now()`，会掷出"隔一毫秒换一次先手"的规律。
  `mersenne` 的种子扩散干净，连续种子的首个输出实测就是均匀且互不相关的。
- **抛硬币排在洗牌之前。** 洗牌会按牌组长度推进 rng，先手要是排在后面，
  换一副牌组或换一份题库就会掷出另一个先手，"同一个 seed 谁先手"这件事就不好复盘了。
- **`rngSeed` 排在洗牌、洗题序之后取。** 同一个道理：rng 是就地推进的，
  往前插一次取值会把后面所有随机结果整体挪位，既有的"哪个 seed 谁先手"全部作废。

**`GameSetup` 另有三个可选覆盖项，用来把随机整个关掉**（教程要按固定剧本演，见 5.3）：

| 字段 | 作用 |
|---|---|
| `questions` | 指定题序，原样使用不再洗。塞一两道题就能几轮打到 `GAME_OVER` |
| `firstPlayer` | 指定第一轮先手，**整个跳过**那一掷（不是掷完丢掉）。之后每轮照常交换 |
| `noShuffle` | 双方牌组和题库都按传入顺序原样使用 |

`firstPlayer` 不消耗随机数是有讲究的：这样同一个 seed 下改先手，后面洗出来的牌堆和题序
一字不差，排剧本时"定牌序"和"定谁先手"两件事互不牵连。
反过来，指定先手和不指定先手在同一个 seed 上洗出来的牌不一样，那是两种玩法，本就不必对齐。

`noShuffle` 时要记住**抽牌是从数组末尾取的**（牌堆顶在末尾）：想让起手是 A、B、C、D、E，
牌组就得写成 `[..., E, D, C, B, A]`。题库相反，按 `questions[round - 1]` 从头往后取。

### 3.5 收藏与抽卡

`src/collection.ts` 定义完整卡池和新玩家的初始收藏，
并提供 `drawNewCard(owned, random)`：从未拥有的卡里等概率抽一张，全部集齐时返回 `null`。

`random` 是外部传进来的 0-1 随机数，不是内部 `Math.random()`——
和引擎一样，core 里不允许有副作用，这样这个函数可以被直接断言。
实际的随机数和存档读写都在客户端（见 5.9）。

眼下卡池是 16 张 AI 牌加 10 张已开放的技能牌，共 26 张。进不了卡池的有两类：
18 张 AI 里 OpenRouter 调不到模型的 2 张（见 `aiModels.ts` 的 `PLAYABLE_AI_CARD_IDS`），
以及 24 张技能牌里「即将上线」的 14 张（见 `skillCards.ts` 的 `OPEN_SKILL_CARD_IDS`；
开放的那 10 张正好就是效果已经接进引擎的 10 张，两份名单是同一批）。
`INITIAL_COLLECTION` 把卡池全解锁了、因此等于整个卡池，
`drawNewCard` 恒返回 `null`——赢一局只涨胜场，抽不到新卡。这条链路是通的，
等卡池扩到超出这份收藏会自动重新生效，不需要改代码。

### 3.6 调试指令

`Command` 里另有四条 `DEBUG_*`，专门给 dev 测试房（见 5.1）用，
让一个人不必真打十几轮就能摆出想看的局面：

| 指令 | 作用 |
|---|---|
| `DEBUG_ADD_CARD` | 给某方加一张手牌：不带 `cardId` 就从他牌堆抽一张，带了就凭空造一张（牌堆不动） |
| `DEBUG_REMOVE_CARD` | 弃掉某方一张手牌，产出新的 `CARD_REMOVED` 事件 |
| `DEBUG_PLAY_CARD` | 无视出牌轮次打出一张手牌（要选目标的技能牌照样得带 `targetInstanceId`） |
| `DEBUG_SKIP_TO_QUIZ` | 跳过双方剩下的出牌，直接进答题阶段 |

三处取舍：

- **走同一条 `execute` 路径，不另开后门函数。** `DEBUG_PLAY_CARD` 直接复用 `playCard`，
  结算一字不差；`DEBUG_SKIP_TO_QUIZ` 复用 `END_PLAY` 进答题那一段，同样发
  `QUESTION_REVEALED`，接着照常由 driver 自动提交答题结果（见 4.5）。
  调试路径和真实路径共用一份代码，测出来的行为才等于真实行为。
  代价是联机时客人发这几条指令房主也照样会执行——本项目本就不防作弊（见 4.1），
  引擎这层不做身份或来源校验，要不要给入口是客户端的事。
- **只有"轮到谁出牌"这一条检查为它们让路**，阶段、手牌里有没有这张卡等等照常检查
  （`DEBUG_PLAY_CARD` / `DEBUG_SKIP_TO_QUIZ` 仍然必须在出牌阶段）。
  测试房要能替对手出牌，但摆出来的局面仍然必须是引擎认可的合法局面。
  加牌和弃牌两条例外地不限阶段：测试房要能在答题阶段先把下一轮的手牌摆好。
- **`CARD_REMOVED` 是为它新增的事件。** 出牌时"牌离开手牌"永远伴随着
  `AI_DEPLOYED` 或 `SKILL_PLAYED`，单纯弃一张牌只有两个来源：这条调试指令，
  以及后来接进来的「模型蒸馏」（弃掉手牌里的一张 AI 换 Token）。

`GameState.seq` 是给凭空造牌兜底的下一个实例序号。造出来的牌要一个不撞车的 `instanceId`，
而引擎里不许有 `Math.random` / `Date.now`（见 3.1），所以这个计数器只能存进状态本身，
才会跟着状态一起被深拷贝、一起发给客人。它从发起手牌时用的那个计数接着往下走，
造出来的 id 带 `dbg-` 前缀，和发牌时的 `p0-c3` 区分得开。

## 4. 联机：房主模式

### 4.1 为什么不做服务器权威

服务器权威要在服务端跑一份规则、做状态同步和校验，
对黑客松来说这部分工作量比游戏本身还大，而它换来的只有"防作弊"——
这场比赛不需要。

### 4.2 谁跑规则

**创建房间的那个客户端（房主）是唯一跑 core 状态机的地方。**

```
房主客户端                 Worker + Room DO                客人客户端
  │                             │                             │
  ├── GET /api/room ───────────>│                             │
  │<────────── 房间码 "4213" ───┤                             │
  ├ WS /room/4213?role=host&peer=… >│                         │
  │<────────── #room:ok ────────┤                             │
  │                             │<WS /room/4213?role=guest&peer=…┤
  │<──────── #peer:joined ──────┤                             │
  │                             │                             │
  │ createGame(seed, 双方牌组)  │                             │
  ├── events ──────────────────>├─────────── >events ────────>│  播动画
  │                             │                             │
  │                             │<────────── command ─────────┤  客人打出一张牌
  │<──────── >command ──────────┤                             │
  │ execute(state, command)     │                             │
  ├── events ──────────────────>├─────────── >events ────────>│  播动画
```

规则很简单：

- **客人只发指令，不算规则。** 它本地不跑 `execute`，只维护一份用于渲染的视图。
- **房主收到双方指令，串行喂给 `execute`，把事件流广播出去。**
  指令天然被房主排成了一条队列，不存在并发和冲突。
- 房主自己的操作也走同一条路径（本地 `execute` → 广播事件），
  这样两边的动画时序是一致的，不用为"自己的操作"写第二套逻辑。

代价是**房主掉线掉够久 = 对局结束**：只有房主在跑引擎，它不回来这局就没法继续。

但"掉线"要熬过一段宽限期才算数。断线本身是常态（切网、锁屏、地铁），
所以连接层做了自动重连、心跳探活和指令重发，链路断了先显示"正在重连"，
满 60 秒还没回来才判中断（细节见 `docs/deploy.md` 第 6 节）。

### 4.3 客人的视图从哪来

最省事的做法：房主在开局时把完整 `GameState` 也 relay 一份，之后客人靠事件流跟着更新。
**不隐藏对手手牌**——藏牌需要给每个玩家算一份裁剪过的视图，
而不藏牌只要广播同一份数据。既然不防作弊，就没必要付这个复杂度。

### 4.4 server 做什么

`packages/server` 是一个 Cloudflare Worker，只做三件事：

1. `GET /api/room` → 摇一个没人用的 4 位房间码，回给建房的人。
2. `GET /room/:code?role=host|guest&peer=<玩家id>` → 升级成 WebSocket，把人放进房间（上限 2 人），
   然后通知房里原本那个人 `#peer:joined`。
3. 收到消息 → 原样转给房里的另一个人，**不看内容**。

外加连接通断时给房里另一个人发 `#peer:online` / `#peer:offline`。

**房里有几个人是按玩家算的，不是按连接算的**：一个玩家断线重连会换一条新连接，
但还是同一个玩家。玩家身份就是 URL 上的 `peer` 参数，转发器靠它把"重连"和
"另一个人来了"区分开，也靠它让重连的人不被自己还没被回收的旧连接挡在门外。

**一个房间 = 一个 Durable Object 实例，房间码就是它的名字。**
同一个码永远被路由到同一个实例，所以不需要维护一张全局房间表——
"房里有谁"就是"这个实例上挂着哪几条连接"。

这个结构顺带消掉了旧转发器上必须手工提防的一个坑：那时一条连接能同时待在两个房间里，
客户端进别人的房前忘了退出自己那间就会转发串台、空房还占着号。
现在一条连接绑定一个房间，换房就是换连接，同时占两间房这件事在结构上就不成立。

连接用 **WebSocket Hibernation** 托管：闲置时 DO 可以休眠，但连接不断、也不计时长费用。
这是免费档能长期挂着对局连接的前提。

服务端发下来的每一帧带一个字符前缀区分两类消息：`#` 是控制消息，`>` 是原样转发的对端载荷。
之所以不包一层 JSON，是因为**服务端绝不解析游戏载荷**——加前缀是纯字符串拼接。
所以服务端不认识卡牌、不认识回合，**协议改了它也不用动**。

### 4.5 答题结果谁来生成

答题是这个游戏唯一"结果不由规则算出来"的一步：一张 AI 牌答没答对，最终要去问真实的模型 API。
而引擎必须是纯函数（见 3.1），不能联网、不能等一个 Promise。所以这件事被切成了两半：

**引擎只接受结果，不生产结果。** 双方出牌结束后引擎进入 `phase: 'quiz'`，发一条
`QUESTION_REVEALED` 就停在那儿等着；结果由 `SUBMIT_ANSWERS` 指令从外面喂进来，
引擎照着它罚下答错的、算出这一轮谁拿分。这条指令玩家点不出来，它代表的是
"场上这批 AI 已经答完了"这个事实。

**生成结果的是跑引擎的那一端**，也就是本地 driver 或联机房主。
`src/match/quizAutopilot.ts` 包在 driver 的 `apply` 外面：每执行完一条指令看一眼局面，
在"从非 quiz 变成 quiz"这个**变化沿**上排一个定时器，约 2.5 秒后把结果提交上去。
认变化沿而不是"当前是 quiz"，是因为答题阶段里测试面板照样能发 `DEBUG_ADD_CARD`，
每条都触发会排出好几个定时器、同一轮被提交多次。
定时器到点时读的是**最新**的局面而不是触发那一刻的快照——这中间玩家还能改手牌，
拿旧快照算出来的结果会和场上对不上，被引擎整条拒掉。
`dispose()` 必须清掉定时器，否则界面都卸载了它还会往一局没人看的对局里发指令。

那 2.5 秒纯粹是留给客户端播"揭晓题目 + AI 作答中"的时间，不追求和动画精确对齐：
动画层收不到结果只是少播一段，不会把局面卡住。

**联机客人不接这一层。** 房主是唯一跑引擎的一方，结果也只由它生成，跟着 `match:sync`
同步给客人；客人也提交的话同一轮会被提交两次，第二次被引擎拒掉，白白多一条错误提示。

**提交完不等于这一轮结束。** 引擎收下 `SUBMIT_ANSWERS` 只把分算完，然后停在
`phase: 'settle'` 等双方各发一条 `CONFIRM_ROUND`（见 3.4），两条都到齐才补牌、换先手、
Token 补满、进下一轮。所以自动驾驶这一层只管交卷，不管翻页——翻页是玩家在结算界面上点的。
联机客人的那次确认走的还是现成的 `match:command` 通道：和出牌指令一模一样地转给房主执行，
新局面再跟着 `match:sync` 回来。转发器只认消息信封、不认指令类型，服务端一行都不用改。

现在结果来自 core 的 `scriptedAnswers`，也就是那份离线预生成的真实模型回答（见 3.4）。
**将来改成对局中途实时调模型 API，只需要换掉 autopilot 里对它的那一次调用**——
`SUBMIT_ANSWERS` 和 `AnswerResult` 的形状、
引擎的时序、界面的动画都不用动。这个分法就是为了那一天准备的：
把"要联网、会失败、要等"的那一步整个挡在引擎外面。

**干扰类技能就落在这一层。** 用户拍板：「复读机」「黑白颠倒」的效果本体是
**往那个 AI 的 prompt 里注入一句话**，注入什么写在 `script.ts` 的 `INTERFERENCE_PROMPTS` 里
（按 `AiInstance.interference` 查），答成什么样交给模型自己。

那两句是**提示词，不是开关**：模型可以照做，也可以不理。「复读机」那句尤其是骗它的
——给模型编一条"本轮答「香蕉」可得双倍积分"的假计分规则，再加一句"你自己权衡"，
赌它上钩；硬命令句谁都会拒，一个划算的假承诺才骗得动。

这两句**已经离线跑过一遍了**：预生成时每道题都按三份上下文（无注入 / 复读机 / 黑白颠倒）
各跑一次，所以命中之后查的就是那个模型在被注入时真说出来的话（见 3.4）。
于是这两张牌的强度本来就不是常数：同一张打在不同模型身上是两个结果，有的当场答香蕉、
有的识破了照常答题——这正是它们好玩的地方，而引擎和界面只认 `AnswerResult`。

`INTERFERENCE_PROMPTS` 里那两句必须和 `scripts/pregen-answers.mjs` 的注入词**一字不差**：
那边跑出来的答案就是这份表的数据来源，文案对不上就成了"界面说注入了 A、播的却是 B 的结果"。
改文案要两边一起改，并重跑预生成。

## 5. client：全部是 React DOM + GSAP

| 层 | 技术 | 负责 |
|---|---|---|
| 唯一一层 | React DOM + GSAP | 全部界面：手牌、场上的 AI、飞出去的卡牌、全屏过场、菜单、状态栏、结算弹窗 |

React 只负责"有哪些元素、它们在什么状态"，**位置和动画一律交给 GSAP 直接改 DOM**。
不要用 CSS transition 做对局动画：一个元素同时被 React 的 class 和 GSAP 的补间改，
两边会互相打断，节奏也没法精确控制。

对局画面的接入方式是**消费 core 的事件流**：收到一个 `GameEvent` 就播一段动画，
播完再取下一个。不要在客户端重算规则。

### 5.1 界面与路由

四个正式界面加若干开发页，路由用 wouter
（2.2KB，API 是 react-router 的子集，将来要换基本只改 import）：

```
/         主网站：介绍 + 「开始游戏」
/info     关于本作：团队名单和黑客松出处，首页导航「信息」进来
/room     匹配房：自己的 4 位房间码 + 输入对方房间码
/match    对局界面（联机对局和 dev 测试房共用）
/tutorial 新手教程：教学开始页 → 教学对战 → 组牌教学 → 选英雄教学 → 完成页，整条流程一条路由（见 5.3）
/dev      开发页导航：把下面这几个开发页连同测试对局列在一处
/design   设计参考页：纸面视觉元素的样板间（开发用）
/deck     组建牌组 demo：假卡池 + 选卡手势（圆圈加减、卡池 ↔ 牌组拖拽、点开放大查看）
/loader   加载动画的演示和调参页：各档参数连同浅色底一起摆开对比
```

后五个是开发页，正式流程里没有入口。开发页各自的路径不必记，从 `/dev` 挑就行
（首页角落的 dev 区也留了快捷方式）；新增开发页时记得往 `dev/DevIndex.tsx`
的 `ENTRIES` 里补一条。`/deck` 选出来的牌组不落盘、也进不了对局，只用来跑通
选卡的手势和版式，真卡池落地后重做。开发页的路径没有统一收进 `/dev/` 前缀：
像 `/loader` 这种就是真实加载场景在用的那一套（`index.html` 的首屏 loader 和
首页等图时的整屏加载页 `ui/LoadingScreen.tsx` 都是同一副样子），短路径方便随手打开对着调。

首页的**「开始游戏」**按存档分流：`tutorialDone` 为 false 就进 `/tutorial`，否则进 `/room`。
分流在点下去那一刻现读存档，不在挂载时读一次——教程和首页之间来回跳时，提前读的那份会过期。
**重玩教程的入口在匹配房**（左上角「新手教程」），它不看 `tutorialDone`，随时进得去；
教程全程右上角还有一颗不显眼的「跳过教程」，确认一次之后写标记 + 进匹配房。
也就是说 `tutorialDone` 只管"要不要自动把玩家送进教程"这一件事，不挡任何手动入口。

首页那张画是十几张整幅切图叠出来的，加起来约 2.5MB。这些图**全部**加载完之前首页不上场，
中途只显示加载动画，免得玩家看着夜空、人物、桌子、道具一层层往上冒。
两头各做了一件事：`index.html` 里给这些图写了 `<link rel="preload">`，下载和 JS bundle 并行；
`HomeScreen` 用 `ui/preloadAssets.ts` 的 `useAssetsReady` 等它们解码完（顺带等字体，
免得标题先用兜底宋体画一遍再跳）。等待有 10 秒超时兜底，图取不到也进得去首页。
`index.html` 那份清单和 `HomeScreen` 里的 `HOME_ASSETS` 要对得上——两边都改，或者都不改。

首页人物的 hover 高亮吃的是同一批图。人物那几层铺满舞台又压在展示卡上面，一收指针事件卡就再也
hover 不到了，所以命中判定改在舞台上监听 `pointermove`，拿 `castHitTest.ts` 预先抽好的 alpha
通道逐像素查（桌面弧和前景道具当遮挡层减掉，免得"指着地球仪高亮它后面的人"）。
抽 alpha 要把七张人物抠图和两张遮挡图各读一遍，但那时它们已经被上面那步拉进缓存了，
不会再走网络。这一步**不**算进加载闸门：抽完之前 hover 静默不生效就是了，
为一个可有可无的反馈多顶一会儿 loader 是每个玩家都要付的代价。

`/design` 把纸张、图标、卡牌、卡背这些视觉元件连同"为什么调成这个值"的说明摆在一页上，
用的就是 `src/ui/paper` 下的正式组件，所以组件改坏了这一页第一个看得出来。

**`/match` 由联机对局和 dev 测试房共用一份界面代码。** 区别只有两样：
`MatchSession` 里放的是哪种 driver，以及跟着 driver 一起放进去的 `testMode` 标记。
测试房用本地 driver，`testMode` 打开后对方手牌从顶边的倒扇形牌背换成摊开的真实卡面
且可点（替对方出牌）、底下挂一块测试面板、结算不记胜场。

特意不给测试房另开一条路由或另一套界面：另开一套的话，在测试房里验过的行为就不再等于
联机时真实会发生的行为，测了也白测。进测试房的入口有三个——匹配房页面底部、首页的 dev 区和 `/dev` 导航页，
都不依赖房间连接建没建起来，一点就地建一局本地对局再跳 `/match`。

原来还有一个 `/dev/hand` 手牌动画演示页，对局界面接了真 UI 之后已经删掉，理由见 5.6。

不引 Next.js 是因为这里是纯客户端游戏：SSR、RSC、服务端数据获取一项都用不上，
每个页面都得挂 `'use client'`，等于把 Next 当成一个启动更慢的 Vite。
它也解决不了部署上的难题——WebSocket 长连接 Vercel 托不住，转发器无论如何都要另找地方跑
（最后落在 Cloudflare Worker + Durable Object 上，见 `docs/deploy.md`）。

**对局状态不放在路由上。** `MatchSessionProvider` 挂在 Router 外面，持有当前这局的 driver，
房间页建好 driver 之后才跨得过跳到 `/match` 的那次卸载。它不写 localStorage，
所以刷新 `/match` 会读不到 driver，直接跳回首页——和「不存对局」是一致的。

### 5.2 MatchDriver：对局的三种来源

本地热座、dev 测试房、联机房主、联机客人，**界面完全一样**，
区别只在于指令交给谁执行、局面从哪来。这层差异收进 `src/match/driver.ts` 的 `MatchDriver` 接口。
四种玩法只对应三个实现：热座和测试房共用 `localDriver`，两者的规则都在本地跑，
差别只在座位怎么定和对方的指令由谁发（见下表）。

```ts
subscribe(fn)        // 局面变了，配 useSyncExternalStore
getSnapshot()        // MatchView：state / seat / status / lastRejection / abortReason
subscribeEvents(fn)  // 每批新事件，给动画层
send(command)
dispose()
```

| 实现 | 谁跑 `execute` | 对手指令来自 | 答题结果 |
|---|---|---|---|
| `localDriver` | 本地 | 同一个页面：热座是坐在旁边的另一个人（`seat: 'active'`，视角跟着行动方走）；测试房是测试面板和摊开的对方手牌（`seat: 0` 固定，视角不换边） | 自己生成 |
| `hostDriver` | 本地 | socket relay | 自己生成，跟着 `match:sync` 发给客人 |
| `guestDriver` | 不跑 | 房主 relay 过来的事件流 | 不生成，等房主同步 |

最后一列就是 4.5 那层自动驾驶：跑引擎的两端才接，客人接了会重复提交。

回合结算的 `CONFIRM_ROUND` 不必另开通道：它是玩家在结算界面上点出来的普通指令，
和出牌走同一条 `send`——本地和房主直接进 `execute`，客人 relay 给房主执行再等 `match:sync`
把新局面带回来。服务端不认识这条指令，也不需要认识（见 4.5 末尾）。

`MatchStage` 只认一个 driver，外加一个 `testMode` 标记（见 5.1）——
它分不出手上这批事件是本地算出来的还是从网络收来的。**接联机时对局界面一行都不用改。**

两条订阅分开是有意的：`getSnapshot` 给的是「事件全部应用完」的结果，负责渲染；
事件流是「过程」，负责播动画。两者节奏不同，混在一起会互相牵制。
事件订阅者只允许一个，换来的性质是**没人订阅时事件会攒着，等第一个订阅者来了补发**——
driver 在构造函数里就把开局事件发出来了，而 React 要等 effect 里才订阅得上，
不攒着的话发牌动画必然丢。

### 5.3 教程（已实现）

流程和文案在 `docs/出牌吧AI_新手教学对战规格_V1.1.md`：一局脚本控制的三轮教学对战，
打完再教组牌和选英雄。方向是**强制玩家按固定流程走一遍操作**，
而不是配一个 AI 对手跟他真打一局——只有每一步都锁死，引导才知道下一句该说什么。

整条流程是 `TutorialScreen` 里的一个 phase 状态：
`教学开始页 → 教学对战 → 过渡提示 → 组牌教学 → 选英雄教学 → 完成页`，全在 `/tutorial` 一条路由内换画面
（同 `RoomScreen` 内嵌选卡组 / 选英雄，理由也一样：换路由就要重建状态，
而"打完这局的比分"要一路带到完成页）。后三屏**不新写页面**，
而是给现成的 `DeckScreen` / `HeroScreen` 各加一个可选的 `tutorial` prop：
那个 prop 只做减法（放行哪张卡 / 哪位英雄、其余操作挡下并喊一声），
不传的两条老入口（`/deck`、`/hero` 和匹配流程）行为一字不变。
组牌教学预填 17 张、留三张让玩家亲手点（两张 AI 牌 + 一张技能牌），
拼好的牌组按固定 id 真写进 `deckStore` 并设为当前牌组，教程结束就能直接开局；
选英雄只放行格蕾丝·霍珀（其余六位暂时锁掉），确认后走 `saveHero` 落盘。
教学局的英雄也是写死的：玩家用霍珀，对手必须挑一位 `comingSoon` 的（现在是李飞飞）——
对手身上任何一条会生效的技能都可能把脚本顶歪（霍珀的 Debug 会抵消玩家第 2 轮那张教学技能牌，
阿达的 Token +2 会让教学局那本 Token 账对不上），见 `tutorial/content.ts`。

**教学对战跑真引擎，不做演出用的假引擎**：教程规则就是正式规则，引擎是纯函数 + 确定性，
教学局天然可预测。为它准备的口子在 core 里（见 3.4 末尾那张表）：
`firstPlayer` 指定先手（第 1 轮玩家先手、第 2 轮对手先手是脚本的一部分），
`noShuffle` 让起手和每轮抽到的牌完全由教学牌组的排列决定，
`questions` 塞三道题——**这三道就是正式题库里的题**（`QUESTION_POOL` 里的 q-mirror、
q-court、q-bamboo），答题结果也和正式对局同源，查 `script.ts` 那张预生成的真实模型回答表。
教程不再有自己的答案表（`quizAutopilot` 的 `answersFor` 这个口子还在，只是没人用了）。

于是"每一轮都只有玩家答对"不是写死的，而是**照那张表挑题、挑牌挑出来的**：
玩家第 1 轮那张 GPT-3.5 在这三道题上都答对，对手脚本那三张（GPT-4o / DeepSeek-R1 / MiniMax）
在各自那道题上都答错，其中第 2 轮那张是被「复读机」注入之后才从「无法判断」改口答「香蕉」的
——玩家刚在卡面上读到"只能回答香蕉"，紧接着就在真实模型的回答里看到它。
换题或换牌都要回那张表重挑一遍，`test/tutorial.test.ts` 按格子对着守。
代价是教学局排不出一个自然的平局（三轮双方答对数都不同），
所以「同结果就比 Token」那条规则改成第 2 轮结算后的一句纯讲解，不在对局里演（规格 §8）。

现在的实现分四块：

| 文件 | 负责 |
|---|---|
| `tutorial/content.ts` | 教学数据：从正式题库挑的 3 道题、双方 20 张牌组、英雄、对手脚本 |
| `match/tutorialDriver.ts` | 包一层 `localDriver`：焊死 `GameSetup`、按脚本替对手出牌，外加事件旁路和对手闸门 |
| `tutorial/steps.ts` | 纯数据的步骤表（规格 §17 的状态清单），每步带高亮锚点、放行范围、提示、完成条件 |
| `tutorial/TutorialController.ts` + `TutorialOverlay.tsx` | 跑步骤表 / 压暗挖洞 + 一句话提示 |
| `tutorial/deckSteps.ts` + `TutorialDeckStage.tsx` | 组牌教学：17 张预填、三步引导、把限制交给 `DeckScreen` |
| `tutorial/heroSteps.ts` + `TutorialHeroStage.tsx` | 选英雄教学：两步引导，确认后 `saveHero` |
| `tutorial/TutorialOutro.tsx` + `TutorialSkip.tsx` | 过渡提示页 / 完成页，以及全程右上角的「跳过教程」 |

两条约定值得单记：

- **教程要有第二条事件订阅**，但 driver 的 `subscribeEvents` 全局只允许一个（那是
  `MatchStage` 的，见 5.2）。所以 `tutorialDriver` 自己订走 localDriver 的事件再扇出，
  给教程的那条叫 `onEvents`，两条各带各的缓冲。
- **对手脚本要能被教程挡住**（`setFoeHold`）。第 2 轮对手先手，它的出牌演出是全屏过场
  （1100），不挡的话会盖在还没讲完的引导提示（1000）上。步骤表里只有明确要它动手的
  那几步才放行。
- **纯讲解的步骤等玩家点一下才走**（步骤表里的 `advance: tap()`）。读一句话的快慢因人而异，
  定时自动跳必然有人没读完就被翻页。引导层为这些步铺一层点击捕获层（那几步界面本来就锁死，
  玩家没有别的可点），气泡里另配一颗「下一步」。推进循环里**一次点击只推一步**：
  推走一步 tap 就把这一下点击划掉，否则连着三步的讲解（如第 2 轮开头那三句）会被一下点完。
  `delay` 现在只用在 `readyOn` 上，等的是一段没有收尾信号的演出。

引导层三屏共用一份（`TutorialOverlay`），坐标口径靠 `ui/battleStage.ts` 自动切换：
对战页和组牌页各有一个 `stage-scaler` 缩放层，量到的是舞台内坐标；
选英雄页没有缩放层（排版是 cqi），那几个函数自动退回视口口径。
唯一要小心的是它挂在哪——`position: fixed` 的包含块是最近的那个带 transform 或布局包含的祖先，
所以组牌页挂在 `.deck-scaler` 里、选英雄页必须挂在 `.hero__stage` **外面**
（它带 `container-type: inline-size`，放进去坐标就从视口变成了舞台）。

引导层压暗、挖洞、提示气泡都放在 `z-index: 1000`：压过对局常规 UI（≤90），
但被全屏过场（1100）盖住——所以每一句提示都挂在某段演出的收尾信号上
（`MatchStage` 的 `onStageCue`，信号清单见 `ui/matchStageTutorial.ts`），
宁可晚一拍出场，也不跟过场抢画面。整层默认 `pointer-events: none`，
"这一步不许点什么"由 `MatchStage` 的限制负责（逐张手牌挂进 `HandFan` 的 `blocked`、
「结束出牌」单独一道闸），不靠遮罩挡；唯一吃指针事件的是等点击那几步的捕获层和「下一步」按钮。

`/tutorial` 刻意不走 `MatchScreen`：那条路径会给胜局记胜场，而教学局是写死结局的剧本。

第一版是三关写死的剧本，已经随提交 `a616a7c` 整体删掉了。

### 5.4 为什么推翻了 Pixi

早期版本用 PixiJS 画对局、React 盖一层覆盖层。实际动手之后换成纯 DOM，原因：

- **对象量级根本用不上画布。** 场上加手牌撑死几十个元素，浏览器排版这点东西毫无压力。
  Pixi 的价值在成千上万个精灵，这里付了复杂度却拿不到收益。
- **中文卡面排版。** 卡牌上是几行中文描述，要自动换行、要省略号、要对齐。
  DOM 里这是几行 CSS，Pixi 里得自己算换行和度量。
- **CSS 3D 翻转是现成的。** 卡牌翻正反面用 `transform-style: preserve-3d` 加一条
  `rotateY` 补间就够了，Pixi 没有原生的 3D 翻面。
  （正反两面谁可见另有讲究，不用 `backface-visibility`，见 5.7。）
- **省掉两层坐标的交接。** 覆盖层和画布各有一套坐标系，
  想让一张牌"从 DOM 的手牌飞进画布的战场"就得手动换算。
  全在 DOM 里之后，跨容器的位移直接用 GSAP 的 Flip 插件（FLIP 技术）补间，不用碰坐标。

**将来要粒子特效怎么办**：在最上面加一层 `pointer-events: none` 的轻量 canvas，
只画粒子，不参与布局和交互。需要的时候再加，现在不预留。

### 5.5 动画约定

- 补间统一用 `@gsap/react` 的 `useGSAP` 创建，它会在组件卸载时把这一片的补间和内联样式
  一起清掉，也兼容 React 严格模式的两次挂载。
  能圈定范围的组件顺手带上 `scope`；像跨容器 Flip 那种要同时够到两个容器的就不带
  （`MatchStage` 里手牌飞进战场那段就是这种）。
- **稍后才执行的回调里新建的补间也要包 `contextSafe`**，不只是事件处理函数：
  `contextSafe` 只在被它包住的那次同步执行期间生效，
  所以 `setTimeout`、`resize` 监听这类回调必须自己再包一层，否则补间不归 context 管，
  组件卸载时 revert 不掉，会继续去改已经脱离文档的节点。
  `useGSAP` 的回调有第二个参数就是 `contextSafe`，在回调里包好存进 ref 最省事。
- 同一个元素上可能有多个补间抢同一个属性（比如快速扫过手牌），
  所有补间都带 `overwrite: 'auto'`，让新补间干净地接管旧的。
- 跨容器移动（手牌 → 战场）用 `gsap/Flip`：改 React 状态**之前**先 `Flip.getState()`，
  在 `useGSAP`（本质是 layout effect）里 `Flip.from()`。
  两个容器里的元素靠 `data-flip-id` 对上号，所以那个 id 必须全局唯一。
- **元素是被 React 销毁重建的（不是同一个节点挪了位置），`Flip.from()` 必须显式传 `targets`。**
  不传的话 Flip 退回用 `state.targets`——那是截取状态时的旧节点，
  此刻已经被 React 从 DOM 里摘掉了，补间会挂在这个脱离文档的节点上，新元素一动不动。
  Flip 不会自己拿 `data-flip-id` 去全文档找新元素，`data-flip-id` 只用来把两份 state 对号。
- **给 `Flip.from()` 传的 `zIndex` 飞完不会自己收**：它是被写死在元素内联样式上的，
  所以每段飞行的 `onComplete` 都要点名 `gsap.set(target, { clearProps: 'zIndex' })`。
  不清的话战场上会同时存在三种层级的小卡（60 / 1200 / auto），有的盖得住手牌有的盖不住，
  停在 1200 的那张连展示遮罩（1100）都能戳穿。只能点名清 `zIndex`：
  `clearProps: true` 会把落位用的 `transform` 一起抹掉。

**对局里那些阶段动画全部挂在 `MatchStage` 那一处 `useMatchEvents` 上**（事件订阅者全局唯一，
见 5.2），分两档：**全屏过场吃掉指针事件**（`z-index: 1100`，演的时候玩家不能出牌），
**中央横幅不吃**（特效层 `z-index: 80`）。

- **开局抛硬币**（`GAME_STARTED`）：全屏挂一枚硬币（正反两面各一张币面图），
  `rotationY` 连转四圈之后落到「先手」或「后手」那一面，停一下再整层淡出。转动补间是这里自己写的
  （要和淡入淡出排进同一条时间线，套不进 `flipCard.ts` 的 `flipTo`），
  但正反两面谁可见仍然复用 `syncFlipFaces` 那套角度硬切，不用 `backface-visibility`，
  原因见 5.7。
- **回合结算全屏层**（`ui/RoundSettleLayer.tsx`，`QUESTION_REVEALED` →
  `AI_ANSWERED` × N → `ROUND_SCORED`，退场看 `phase`）：一层盖住整个战场，
  先亮题面、留四秒读题，再擦出标准答案，然后逐张结果卡淡掉「作答中」转圈、
  打字打出回答和理由、盖上判定章，最后落下本轮结论、比分跳一下，
  「进入下一轮」按钮这才解锁。双方都确认、`phase` 离开 settle 之后整层淡出。
  它的动画**全部内聚在这个文件里**（`MatchStage` 那边一条时间线都不加），
  按「入场 / 新结果卡 / 主线 / 退场」分成四段 `useGSAP`：结果卡是 `AI_ANSWERED`
  一条条到的，也就一张张出现，那一段只能跟着卡片数量走，塞不进入场那一段。
  **答题结果渲染在这一层内部，不去动战场上那张小卡**：事件是在 React 提交新快照**之前**
  送到的，提交一完成，答错的 tile 立刻就从战场上消失了，根本没有机会在它身上播罚下动画。
  所以这层刻意盖住战场，把那次跳变藏在自己后面。
- **结算层的数据是两路口径，别混着用**：内容（题面、谁答了什么、本轮的正确数 / 消耗 / 得分）
  一律吃 `MatchStage` 按事件攒出来的那份 `RoundSettle`——答错的 AI 在新快照里已经被罚下、
  从场上消失了，只有 `AI_ANSWERED` 里还留着它是哪张卡、答了什么
  （事件特意带一个 `cardId` 就是为了这个，见 3.4）；
  而确认态读的是快照（`phase` / `settleConfirmed`）：settle 本就是引擎特意留出的
  "局面不再变"的一段（见 3.4），这两样在整层立着的期间是稳的，比再攒一份事件可靠。
  按钮三态是「可点 → 已确认（等对方）→ 阶段一离开就整层退场」，
  本端另存一个"刚点过"的本地标志：联机客人的确认要绕房主一圈才回得来，
  光看快照的话这中间还能再点一次，第二条会被引擎当成"已经确认过了"拒掉，白弹一条错误提示。
- **技能牌亮相**（`SKILL_PLAYED`）：双方都在战场中央把卡面亮一下再进弃牌堆。
  技能牌不上场，不亮出来的话画面上根本看不出有人打过牌。
  事件带 `targetInstanceId`（打向战场某个格子的那三档目标）时，亮相之后那张卡不再原地淡出，
  而是**飞向目标格**并在落点播一次命中特效（`playSkillHitFx`：目标格轻抖一下 + 边缘追光闪一圈，
  比上场特效轻一档，不震屏也不扬尘）。敌我两边共用这一段：我方从 `.battle__skill-show` 起飞，
  对方从展示位起飞（见 5.8）。「模型蒸馏」打的是手牌，引擎刻意不给它带 `targetInstanceId`
  （客户端拿去战场上找格子会扑空，见 3.4），所以它只亮个相。
  格子上的本轮标记跟着快照渲染，不靠动画残留：`affectedBy` 里每一张牌挂一枚
  （「复读中」/「已颠倒」/「已净化」/「保送」/「已进化」，文案表见 `ui/tileMarks.ts` 的
  `SKILL_EFFECT_MARKS`；表里查不到的落到通用的「被影响」），几枚可以同时挂，
  所以摞成一列（`.battle__tile-marks`）。角标写的是**状态**而不是牌名，
  牌名留给放大查看时卡下面那行「本轮受影响：……」字幕（`affectedCaptionOf`）。
  被金钟罩罩着的那一方，场上每个单位也挂一枚「金钟罩」、字幕里也算一张——它记在
  `PlayerState.shielded` 上而不是单位身上（连本轮之后才上场的单位一起罩着）；
  侧栏自己的面板上另有一枚（`.battle__shield-mark`），
  因为场上一个 AI 都没有时它照样生效，那时卡上就没地方挂了。
- **选目标**（客户端自己的一档，没有对应事件）：标了 `target` 的技能牌打出时不直接发指令，
  先让玩家指一个目标。四档目标（`'foe-ai'` / `'own-ai'` / `'own-affected-ai'` / `'own-hand-ai'`，
  口径见 3.4）共用同一套交互，区别只在**哪一批东西亮着**：前三档亮的是战场上的小卡
  （分别是对方未被干扰的、己方未被保送的、己方正被干扰的，算在 `boardTargetsOf` 里，
  和引擎那几句校验一一对应），敌我两行都可能亮；`'own-hand-ai'`（模型蒸馏）亮的是
  **自己手牌里的 AI 牌**。**两条路都通，随玩家习惯**，
  分岔点是 `HandFan` 的 `onPlay(id, via)` 那个 `via`（`'drag'` / `'tap'`）：

  - **拖出来**（`'drag'`）：牌一离手（`HandFan` 的 `onDragStateChange` 通知上来），
    该亮的那一行里每张合法目标就亮一圈会呼吸的**橙色**描边。松手时按**牌自己的中心**
    找落在谁身上（`dropTargetOf`，四边各放宽 `TARGET_SNAP` 44px，重叠时取最近的一张，
    照炉石那种"差不多就行"的手感），命中就带着 `targetInstanceId` 发出去；
    落在战场空处按"没受理"处理，牌自己飞回扇形。**这条路不压暗**：
    拖着的牌在扇形里（`z-index: 20` 的层叠上下文），压暗层会连它一起压黑，
    合法目标也因此不能抬层级，只亮圈。
  - **点一下**（`'tap'`）：进选目标态，全屏压暗（`.battle__targeting`，`z-index: 75`，
    压过顶栏 70、侧栏 30、手牌 20），亮着的只有两样：合法目标的小卡（抬到 76）
    和整个手牌扇形（抬到 77，`.hand-fan[data-casting]`）。那张正在施放的牌**留在扇形里**
    抬高一点、单独亮着，同排其余的牌由 `HandFan` 用 GSAP 把 opacity 压到 0.3
    （那一层的 opacity 归它管，CSS 插一手会打架），而且整排不再吃指针事件——
    点出这张牌时指针多半还压在它身上，留着 hover 它会一直保持 1.9 倍放大把战场挡死。
    点中目标就发指令，点压暗层任意处、点「取消」按钮都是退出。
  - **选手牌那一档**（`'own-hand-ai'`，只有模型蒸馏）：拖和点都进选目标态——它要选的目标
    根本不在战场上，拖到场上再喊一句"松手要落在 AI 上"只会把人骗进死路。
    候选卡摊成一排铺在压暗层正中（`.battle__hand-pick`），按下即选。
    刻意不去点亮扇形里的原牌：选目标态下整排手牌是冻着的（见下面那段），
    要在扇形里点选就得在 `HandFan` 里另开一条交互路径，而这里要玩家做的判断只有"弃哪一张"。

  两条路共用同一圈橙色描边（GSAP 循环补间，只补间描边那一层——小卡自己那几层的 transform
  归 Flip 和 `cardTilt`，见 5.7）。对手出牌、进答题、出牌权一走也一律当取消。
  **点击路那一套（压暗 + 橙圈 + 顶部提示条）还兼着主动英雄技能的发动**，见下一条：
  `TargetingState` 是个可辨识联合（`'skill-card'` / `'hero-skill'`），
  两档只在"哪几张小卡算合法目标"和"选完发哪条指令"上分岔。
  **两条路都要在 `onPlay` 里同步给出结果**：受理就锁上 `HandFan` 的 `disabled`
  （发指令等回包，或者进选目标态），不受理就什么都不做、让牌下一帧自己飞回扇形
  （约定见 5.6 和 `HandFanProps.onPlay`）。
  这段期间手牌整排冻住（`HandFan` 的 `frozen`，见 5.6）：指针八成还压在刚点出去的那张牌上，
  不冻的话它会一直保持放大，把要选的战场挡死。
- **英雄技能抵消**（`SKILL_CANCELED`）：和抛硬币、回合结算同一档的全屏过场（`.skill-cancel`，
  1100、吃指针事件），大字打出技能名，下面一行说清「谁发动了什么、抵消了你/对方的哪张牌」，
  停一秒多自动淡出。「你/对方」按事件的 `player` 和本端座位比出来，卡名查 `getCard`。
  **它必须等技能牌亮相演完才上**：`SKILL_CANCELED` 和它对应的 `SKILL_PLAYED` 是同一批事件，
  收到时那张牌的亮相（我方 `skillShow` / 对方强制展示）刚开始演，这一层直接盖上去，
  玩家就没看清被抵消的是哪张牌。做法是把待演的文案存进一个 pending ref，
  在 `skillShow` 时间线的收尾和强制展示的收尾里各喊一次 `pumpSkillCancel()`；
  事件到达时没有演出在放就当场放出来。`skillShow` 那边用**计数**而不是布尔记"还在演几段"，
  连打两张技能牌时上一张的时间线还在跑，布尔会被第一条收尾提前清掉。
  它也和另外两层一样是横幅和强制展示的闸门（`cancelUpRef`），收尾里清 state、清 ref、
  补播憋着的横幅。结算层上来时待演的那条直接丢掉：等结算层演完再补一遍，
  就成了下一轮开头凭空冒出来的一句话。
- **主动英雄技能**（`USE_HERO_SKILL` → `HERO_SKILL_USED`）：发动入口是我方英雄牌左下角那颗
  印着技能名的按钮（`.battle__hero-skill`），只有陈丹琦和梅拉妮·珀金斯有（见 3.4）。
  `actionsLocked`（和「结束出牌」同一份口径）或者场上一个打得着的单位都没有时按钮灰着——
  合法目标提前用 `upgradeTargetOf` / `downgradeTargetOf` 各算一遍，链顶链底和只有一代的那几张
  都算不上，不然玩家点进选目标态才发现整场没有一张亮着。技能用掉之后整颗按钮撤走，
  剩下卡面灰化加「技能已用」角标。
  按下进的就是上面那套选目标态，只是合法目标换成"己方升得动的"（陈丹琦）或
  "对方降得动的"（珀金斯）——**我方那一行也会亮**，这是它和干扰技能唯一的排布差别——
  选中就发 `USE_HERO_SKILL`。这条链路不上演出锁：没有牌在飞，手牌也不参与。
  收到 `HERO_SKILL_USED` 播一条横幅（「精准检索！GPT-2 → GPT-3.5」，前后两张卡名只有事件里有，
  新快照里只剩换完那张），再在目标格上播一次 `playSkillHitFx`。
  卡面本身不用管：战场小卡是按实例当前的 `cardId` 渲染的（`handCardOfAi`），
  新快照一提交就换了脸。那个单位从此挂着「已升级 / 已降级」角标（跟着 `AiInstance.levelShift`，
  和干扰、「保送」那几枚排成一列，可能同时挂着两三枚）。
- **AI 上场**（`AI_DEPLOYED`）：我方那张走 Flip 从手牌原位飞进战场，不再叠进场动画；
  对方那张只能排队等下一次提交后播一个弹出——收到事件那一刻它的 DOM 还不存在。
- **被技能牌罚下**（`AI_REMOVED`，内存紧缺 / 国产替代）：事件是在 React 提交新快照**之前**
  送到的（见 5.8），那张小卡此刻还在场上，于是趁这一下把它**原地复制一份**塞进特效层，
  让副本沉下去化掉、脚下扬一把灰（`playRemovalFx`），真正的格子随下一次提交无声消失。
  复制品必须摘掉 `data-flip-id` / `data-ai-id`：战场里好几处按这两个属性查元素，
  留着会抓到这个正在淡出的幽灵。和答错罚下（`AI_ELIMINATED`）分工不同——那一档整个被
  回合结算层盖着，跳变没人看得见，所以不演。
- **进化**（`AI_TRANSFORMED`，鸡犬升天）：还是同一个单位换了卡面身份，换图这件事 React
  跟着快照自己就做了。演出攒到**提交之后**再播（`evolveQueueRef`，同 `popQueue` 的路子）：
  在事件回调里当场演的话，闪的是即将被换掉的旧卡面。演的是边缘追光扫一圈 + 卡弹一下
  （`playEvolveFx`），演完那个单位本轮一直挂着「已进化」角标——换脸本身不在单位上留状态，
  不记进 `affectedBy` 的话，本轮结束前谁都看不出它是被哪张牌变成现在这副样子的。
- **保送留场**（`AI_SAFE_PASSED`）：结算层里那张卡照常画成"答错"（红章、正文压暗，
  它在计分里也确实算答错），只在判定章下面补一枚「保送留场」，说明它没被罚下。
- **发牌**（`CARD_DRAWN`）：新牌从侧栏那摞卡堆飞进自己的扇形槽位，两排手牌各有一份实现
  （`HandFan` / `OpponentFan`，见 5.6）。**发牌一律要等盖住屏幕的那层全屏过场退场再飞**：
  开局那 5 张等抛硬币演完，每轮的补牌等回合结算层淡出——推进轮次的是后手确认的那一下，
  `ROUND_CONFIRMED` 和 `CARD_DRAWN` 是同一批事件，收到时结算层（1100）还整个立着
  （它要等这批事件带来的 `phase` 变化才开始退场），不拦的话牌就在遮罩后面飞完了。
  闸门是 `MatchStage` 的 `dealHeld`（喂给两排扇形的 `dealHold`），两处各配一条兜底定时器，
  防着过场因为任何原因没跑到收尾、牌永远压在卡堆上。
  **开局那条兜底到点时还要再看一眼"硬币是不是正演着"**（`coinUpRef`），
  不能只靠"收到 `GAME_STARTED` 就撤掉定时器"：开发模式的 StrictMode 会让那条 effect 跑两遍，
  而攒着的开局事件只补发给第一个订阅者一次（见 5.2），第二遍建的定时器没人撤，
  0.8 秒后就把牌放出去了——硬币还在转，两段动画同时播。ref 跨 StrictMode 的重挂载是活的，
  所以这道门认得出来。判"这一批要不要拦"看的是
  `ROUND_CONFIRMED` 后面还跟不跟着 `CARD_DRAWN`：先手确认那一批只有 `ROUND_CONFIRMED`、
  局面没推进，最后一轮双方确认后跟的是 `GAME_OVER`、没有补牌，拦了就再没人来放行；
  测试面板的加牌只有 `CARD_DRAWN`、不该等遮罩，该当场就飞。
  放行的落点是结算层退场动画的收尾（`RoundSettleLayer` 的 `onExited`），
  和"补播憋着的横幅"是同一处。
  **整段发牌期间 `actionsLocked` 锁着**（手牌 `disabled` + 「结束出牌」按钮变灰）：
  牌还压在堆上或者还在半空中就出得了牌的话，进场补间会和出牌那段 Flip 抢同一批属性。
  同时手牌进灰墨态（`lockReason` 的 `'deal'`，点一下弹「发牌中…」），
  和「对方出牌中 / AI 答题中」是同一套画法；每轮补牌那次直接从 `'quiz'` 接过来，
  灰墨态一路不断，最后一张落地才和 `actionsLocked` 在同一次提交里一起松开
  （必须同一次，`HandFan` 那个"解锁抖一下整排牌"的判据要回头读 `disabled`）。
- **轮次横幅**（`ROUND_STARTED` / `PLAY_TURN_STARTED`）：一次只播一条，多的排队。
  一批事件里常常连着来两条，同时画在屏幕正中会糊成一团。
  **全屏过场在场时横幅只入队不播**，等过场淡出的 `onComplete` 再把攒着的放出来：
  横幅在 80、过场在 1100，过场期间播等于播给遮罩看；而且双方一确认，下一轮的横幅
  马上就跟着新局面来了，那时结算层还在演退场，正常播的话就白白用掉了。
  "过场在不在"用 ref 记而不是读 state——一批事件是在同一次回调里同步处理完的，
  这中间 React 还没重渲染，读 state 拿到的是"过场没开始"的旧值。
- **对局中断时强制收掉过场**：回合结算层要等双方确认、`phase` 离开 settle 才退场，
  而对手断线时那一步永远不会到来；终局结算层在它下面（90 < 1100），
  不清掉的话玩家会被一层退不掉的遮罩挡死。做法是直接把 `roundSettle` 置空、让 React 把整层卸掉
  （这条路不播退场动画，`useGSAP` 的 context 自己 revert）。
  抵消层和它待演的那条文案一并收掉，同样的理由。

### 5.6 手牌组件

`src/ui/HandFan.tsx` 是通用的扇形手牌，只认自己的 `HandCardData`（字段照着 core 的 `Card` 取名）：
`kind`（`'ai' | 'skill' | 'hero'`）、`name`、`text`、AI 牌才有的 `model`，
外加两个 core 里没有、由调用方拼出来的展示字段——翻面时的补充说明 `backText`
和插画地址 `art`（不填就按 id 稳定地分一张占位图）。
出牌不花资源，所以卡面上没有费用角标；场上的 AI 也没有会变的数值，
战场小卡直接读卡牌定义就够（哪天有了增益/削弱，这里要改成传实例的当前值）。
卡面尺寸要动的话，`--card-w/--card-h` 和 `ui/fanMath.ts` 里那对常量得同步改（见下）。

另有两个口子专为"打出时要选目标"开（用法见 5.5）：
`onDragStateChange(id | null)` 报告现在拖着哪张牌，父组件据此把场上的合法目标标出来；
`castingId` 指出哪张牌已经点出去、正在等玩家指目标——那张牌留在扇形里抬高一点单独亮着，
同排其余的压暗。它是"已打出待受理"记录（`playedRef`）里的例外：那些牌停在落点上不参与排布，
它却要照常排回扇形。选目标期间"整排不接指针"那件事不归它管，由 `frozen` 一起打开。

「这一张打不起」是逐张的另一条线：传 `tokens` 之后按各张的费用判，只压暗买不起的那几张。
判费用用的是调用方给的 `playCostOf`（对局界面转手交给 core 的 `effectivePlayCost`，见 3.4），
不是卡面印的 `tokenCost`——「核电站」开着时真正扣的是打折价，按卡面判会把打得起的牌画成灰的。
不传 `playCostOf` 就按卡面原价判，牌组页这类没有局面可问的地方走的是这一档。

**三个"关掉手牌"的开关分工不同，别混**：`disabled` 只管出不了牌（不是我的回合、等回包），
玩家照样能 hover 抬牌看；`frozen` 是整排彻底冻住（连 hover 和问号翻面都不接），
给"屏幕上正在演一段动画"和选目标态用——那时抬起来的牌会盖住正在演的那张
（放大后的手牌高约 400px，必然戳进我方战场行，而扇形是 `z-index: 20` 的层叠上下文，
落位后的战场格子压不过它，只能不让 hover 发生）；`castingId` 则只管排布。

`kind: 'hero'` 的卡永远不会出现在手牌或战场上——英雄不进牌组，只是借这套卡面画出来：
对局左侧栏每位玩家名字旁边那张小英雄牌（`.battle__hero`，按 `--hero-card-scale` 整体缩小，
和战场小卡一个路子）。它的卡面数据只有一份拼法，
在 `ui/heroCard.ts`（正面印技能、背面印人物），两处共用。
Debug 用掉之后那张小卡整块置灰、底下的标签变成「Debug 已用」——技能一局只发动一次，
玩家得能一眼看出还指不指望得上。

发牌那几个口子（`getDealOrigin` / `dealHold` / `onDealPendingChange` / `onDealBusyChange`）
两排扇形是同构的，`OpponentFan` 那份只是照抄一遍改了方向。后两个通知别混：
`onDealPendingChange` 在牌**起飞**那一瞬就销账（卡堆上的数字得那时候减），
`onDealBusyChange` 要等牌真的**落位**才清，父组件拿它锁住整段发牌期间的操作（见 5.5）；
被 `dealHold` 压着的牌也算 busy——牌已经在手牌数据里了，只是还没开始演。
发牌期间只喂 `disabled` 不喂 `frozen`：`frozen` 一变就要重排一遍手牌，
而重排会亲手掐掉正在飞的进场补间，等于自己打断发牌动画。

扇形的布局数学（`fanTransform` 和那批常量）在 `ui/fanMath.ts`、翻面在 `ui/flipCard.ts`，
都从 `HandFan` 里提了出来，和对手的倒扇形 `OpponentFan`、强制展示层共用一份。
拖拽那台指针状态机（位移阈值、指针捕获、跟随、落点判定）同样提了出来，在 `ui/useCardDrag.ts`，
和 `/deck` 组建牌组页共用一份手感；它不知道牌本来该摆在哪，
排布、邻牌让位、失败之后送回哪里都留在调用方的回调里。

原来另有一个 `src/dev/HandDemo.tsx` 演示页（`/dev/hand`），拿占位数据跑扇形和拖拽的各种边界，
现在**已经删掉**：它那套布局和交互原样并进了 `MatchStage`，也就是真对局界面本身。
再留一份喂假数据的副本，只会变成两份慢慢分叉的实现。
要拿各种局面试边界就进 dev 测试房（见 5.1），那里的卡和结算都是真的。

hover 放大最容易出的毛病是抖动：卡放大之后指针落到了卡外面，于是缩回去，
缩回去又被 hover 到，无限循环。这里靠两条几何约束根治：

- 每张牌以**底边中点**为变换原点，hover 时只放大、只往上长，绝不往下移；
  默认状态下卡牌本来就沉在视口底边以下一截（只露出 85%），hover 时卡底也还在视口外。
- 放大倍数有下限。扇形两端的牌是斜的，斜着的卡角比正放时横向伸得更远
  （倾角 θ 时伸到 `卡宽/2·cos θ + 卡高·sin θ`），放大后的卡半宽必须够到那里。
  代码里这个下限由 `MAX_SPREAD_DEG` 和卡面尺寸算出来（`MIN_HOVER_SCALE`），
  改扇形角度时自动跟着变，不用手工对表。

两条凑齐，放大后的卡才真的盖住了原来那张卡**露在屏幕里的全部像素**，指针掉不出去。
少了第二条，最外侧那张牌的外上角会露在放大后的卡外面，指针停在那一小块上就开始抖。

**出牌有两条路**（炉石式）：

- **拖**：按住卡面走过 4px 才算拖拽，拖进 `dropZoneRef` 指的那块区域再松手才调 `onPlay`，
  松在别处（包括拖回手牌上方）一律飞回扇形。鼠标和触屏完全一样。
- **原地轻点**：没走过 4px 就是点了一下。**这一条按 `pointerType` 分岔**，
  是全组件唯一一处两种设备不一样的地方（见 `handleTap`）：
  - 鼠标 —— 直接调 `onPlay` 打出，不用真的拖进战场，也不存在"落在别处"的取消场景；
  - 触屏 —— 只是把这张牌**选中**：保持抬起放大不再落回去，顶上冒出一颗「打出」匾额
    （`.hand-fan__play`，复用 `PlaqueButton`），点它才调 `onPlay`。再点一次同一张牌、
    或者点到手牌以外任何地方，都是取消选中。
    手指划过屏幕太容易蹭出一次点击，而出牌不可撤销，这一步确认是必须的；
    鼠标点哪儿是哪儿，多这一步只是拖慢节奏。

两条路殊途同归，`HandFan` 自己不区分是哪种触发的——只是把是哪一种（`via: 'drag' | 'tap'`）
一起报给 `onPlay`，因为要选目标的技能牌两条路的后续完全不同（见 5.5）。
触屏那颗「打出」不单开一档 `via`：对父组件来说它和鼠标轻点是同一件事，
多一档只会让每个判 `via` 的地方都要多写一个分支。几个要点：

- 用原生 pointer 事件 + `setPointerCapture` + GSAP 自己实现，没上 `Draggable` 插件。
  想要的是"卡牌中心带缓动追光标"的手感，而 `Draggable` 的刚性抓取偏移
  在从 hover 的 1.9 倍缩到拖拽的 1.1 倍时会看到明显跳变。
- 跟随用 `gsap.quickTo` 只补间 `x/y`，姿态（转正 + 缩放）另起一个补间只管 `rotation/scale`，
  两组属性不重叠才能同时跑；进入拖拽那一下的缩放位移由跟随的缓动吃掉，画面上看不见跳。
- 落点判定看**指针坐标**在不在落点区的矩形里，不是卡牌和它相交——
  这样卡画得多大、歪多少都不影响落点。
- **触屏拖拽时牌整体抬到手指上方半张卡**（`TOUCH_DRAG_LIFT`），手指托在卡的下沿，
  不然要看的东西全被指头盖住。由此带来一个刻意的错位：落点判定看的是**指针**，
  而选目标的命中判定看的是**牌自己的中心**（`MatchStage` 的 `dropTargetOf`），
  触屏上两者差着半张卡——这正是想要的，玩家瞄的是牌盖住了谁。
  战场落点区下沿离屏幕底边还有 250px，手指够得进去。
- 落点区的高亮由 `useCardDrag` 打两个 data 属性在落点元素上：
  `data-drop-ready`（正在拖牌）和 `data-drop-hot`（指针已经进来了），样式在 `styles.css` 里。
  父组件还可以传 `returnZoneRef`，让“放回手牌”区域得到同样的两级反馈；它只负责提示，
  不改变“只有落进 `dropZoneRef` 才算打出，其余位置都取消”的规则。
- 拖出来的那张牌不参与扇形排布，剩下的牌按"少了一张"重排，手牌会合拢。
- **拖拽期间倾斜自动失效**，靠的是 5.7 那个 `enabled` 回调而不是额外的开关：
  它判的是"这张牌是不是当前 hover 的那张"，而进入拖拽的第一件事就是把 hover 清空，
  于是 `attachCardTilt` 只会归零收手、不再往倾斜层写角度。抓起来那一下还会主动调一次
  `reset()`：hover 时攒下的倾斜留着不管的话，拖着一张歪的牌满屏找落点观感很差，
  而指针已经被 capture，等不到 `pointerleave` 自己来归零。

**两个「关掉手牌」的开关分工不同，别混用**：

- `disabled`：出不了牌，但**照样能 hover 把牌抬起来看**。给"不是我的回合"、
  "指令发出去了正在等回包"这类时刻用——轮不到自己时玩家还是想看清手上有什么。
  它同时是异步出牌那套约定的判据（打出的牌停在落点上等结果，见 `HandFanProps.onPlay`）。
- `frozen`：整排手牌彻底冻住，不接 hover、不接问号翻面、也拖不出牌。
  给"屏幕上正在演一段动画"的时刻用。

两个开关打开时都会把触屏那个**选中态**一起收掉（那颗「打出」点了也没用），
`castingId` 变化和被选中的牌离开手牌时同理。这几处在 `HandFan` 里各有一个 effect。

`frozen` 是为了一个几何上躲不开的遮挡：`.hand-fan` 是 `fixed + z-index: 20` 的层叠上下文，
整排手牌对页面恒定是第 20 层（里面每张牌的 `z-index` 只在扇形内部有效），
而 hover 放大后的牌高约 400px，必然戳进我方战场行。牌落位之后 tile 回到 `z-index: auto`，
压不过第 20 层——也就是说"抬起来的手牌盖住刚落场那张牌"在 `HandFan` 内部调层级是修不好的，
只能不让 hover 发生。所以 `MatchStage` 在**有牌在飞或刚落地**（我方出牌、对手的牌从展示位
飞向战场、放大查看飞回原格）以及**展示层演着**的时候把 `frozen` 打开。

实现上有两处容易漏：

- 光在 `handleEnter` 加闸不够，**必须把已经抬起来的那张牌主动收回去**。
  `hoverRef` 不清空的话，冻结期间的一次 `resize` 或者一次手牌增减（出牌成功那次
  `cards` 变化必然落在冻结期内）都会重排一遍，那张牌又被摆回放大位。
  收拾清单和抓起牌时是同一份：停延迟缩回 → 清 `hoverRef`（顺带关掉倾斜跟随，
  5.7 那个 `enabled` 判的就是它）→ 显式 `reset()` 让倾斜和高光归零 → 重排。
  显式 `reset()` 不能省：冻结时玩家指针往往停着不动，`pointermove` / `pointerleave`
  一个都不会来，倾斜角和高光会原地冻住。
- 开关要走 ref。`applyLayout` 被存进 `layoutRef`，那份闭包只在 `cards` 变化时才重建，
  `frozen` 一变它不会刷新。

### 5.7 卡面的倾斜跟随和高光

`src/ui/cardTilt.ts` 提供 `attachCardTilt(el, opts)`：指针在卡面上移动时，
卡跟着指针做小幅三维倾斜，同时一小块白色高光跟着指针跑（模拟覆膜反光）。

**触屏上整套关掉**：`onMove` 头一句就按 `event.pointerType` 挡掉非鼠标的指针。
手指本来就压在卡面上，倾斜看不出来、高光那一小块基本被指尖挡着，
而这两样每次移动都要写一层 transform 和一次渐变，在手机上纯属白烧帧。
判的是每次事件的 `pointerType` 而不是设备类型——带触屏的笔记本用鼠标操作时照样有。
手牌里只有 hover 放大的那张启用（扇形里的小卡本身是斜的，再叠倾斜会乱），
战场小卡则一直启用，幅度稍大一点补偿它显示得小，并且顺带做 5% 的 hover 放大
（`opts.hoverScale`）。放大**只能**走这个选项、不能写 CSS 的 `:hover`：
GSAP 接管一层的 transform 之后会往内联样式里写死 `translate/rotate/scale: none`
来中和那三个 CSS 独立属性，任何 CSS 规则都会被它压住（实测完全没反应）。

**关键是 transform 分层**。一个元素只有一个 `transform`，几件事挤在一层就是互相覆盖，
所以每层只负责一件事：

| 手牌 | 战场小卡 | 负责 |
|---|---|---|
| `.hand-fan__slot` | `.battle__tile` | 摆位：扇形的 x / y / rotation / scale；小卡这边是 Flip 飞行 |
| `.hand-fan__tilt` | `.battle__tile-tilt` | 跟着指针的倾斜：rotationX / rotationY（手牌这一层还挂着 `zoom`，见下；小卡的 hover 放大也在这一层） |
| `.hand-fan__inner` | — | 翻到背面的 3D 翻转：rotationY 180° |
| — | `.battle__tile-inner` | 写死在 CSS 里的一条 `scale`，把整张 150×210 的卡面缩到小卡尺寸 |

战场小卡多出来的那一层是为了**整张卡等比缩小**，而不是重画一套小卡面：
卡面组件（`HandCardFace`）和手牌共用同一份，字号内边距全按大卡写死，缩放交给这一层。

**手牌的 hover 放大不能靠 transform 撑大**，否则放大后的卡面是糊的。
Chrome 对带 3D 旋转的元素走贴图路径：先按**布局尺寸**把整棵子树栅格化成一张贴图，
再把贴图贴到三维平面上。倾斜一生效（实测 0.3° 就够），靠外层 `scale` 放大的卡就是
那张 150×210 的贴图被拉伸 1.9 倍，字和插画都发虚。

所以手牌反过来做：`.hand-fan__slot` 的盒子直接按放大到顶的尺寸布局
（`--card-w/--card-h` 乘 `--hand-card-zoom`），`.hand-fan__tilt` 用 `zoom` 把卡面内部那套
照 150×210 写死的 px 一起放大成真实布局，静置时再由 slot 的 `scale` 缩回去
（`HandFan` 的 `slotScale`：传进去的是"想让人看到多大"，出来的是写给 GSAP 的值）。
于是放大到顶那一刻卡面的 `scale` 正好是 1，按 285×399 排版也按这个尺寸栅格化。

两个配套约束：

- `--hand-card-zoom` 由 `HandFan` 写在 `.hand-fan` 上，值就是 `HOVER_SCALE`
  （按扇形最大倾角算出来的，见 5.6），CSS 里不能再写死一份。
- `zoom` 只能落在倾斜层或更里面。slot 上的 `x / y` 平移会被 `zoom` 乘一遍，
  扇形摆位的坐标就全错位了；倾斜层上 GSAP 只写角度，才轮得到它。
  同理，扇形几何（`fanMath` 的 `CARD_WIDTH/CARD_HEIGHT`、拖拽跟随的偏移）
  用的一律是**显示尺寸**那套口径，和 slot 盒子实际有多大无关。
它必须独立于上面两层——`scale` 混进 Flip 飞行那一层会被飞行补间覆盖掉，
混进倾斜层则会被 cardTilt 每帧写的旋转覆盖掉。

倾斜层和翻转层要 `transform-style: preserve-3d`，否则翻转层会被压成一张平面图片再倾斜。
但这两层平时是 `flat` 的，**只在真的用得上三维的那几秒才切过去**：`preserve-3d` 的含义是
"别把这棵子树拍平"，于是一张卡里十几个节点浏览器一个都不能合并、全部各占一层，
一排五张手牌常驻开着就是几十层白烧，而绝大多数时候手牌是静止摊在那儿的。
开关有两个来源、各打各的属性，互不干涉所以不用引用计数：`ui/cardTilt.ts` 在开始跟随指针时
往 slot 上打 `data-tilting`（和高光的 `data-glare` 同生共死），`ui/flipCard.ts` 按**角度是否为 0**
往翻转层上打 `data-flip3d`——判角度而不是判"补间在不在跑"，是因为牌停在背面时补间早就结束了，
可那一面正靠 `rotateY(180°)` 立着，这时候拍平会当场变成一张水平镜像的正面。
两处都是先打属性、后写变换，落在同一个同步块里，不会出现"3D 还没开、角度已经写了"的那一帧。
规则见 `styles.css` 里 `.hand-fan__inner` 后面那条。

透视（`perspective`）加在最外层，对下面几层一起生效，不用逐层加。
小卡的倾斜层同时承担裁剪（`overflow: hidden` + 圆角）：裁切边跟着卡一起转，
放在不动的 `.battle__tile` 上的话，倾斜时卡角会被一条直边削掉。

**翻面：立体感靠 `rotationY`，正反互斥靠角度驱动的 opacity 硬切，不用 `backface-visibility`。**
所有会动翻转层 `rotationY` 的地方都必须走 `ui/flipCard.ts` 的 `flipTo()`
（`HandFan` 里有四处：hover 问号翻过去、离开问号翻回来、离开整张牌时 `applyLayout` 兜底、
从背面被拖出去时先转回正面；只有技能牌翻得起来），漏一处那张牌就会卡在正反都显示的样子。
自己写 `rotationY` 补间的场景（`MatchStage` 的抛硬币要连转数圈、还要和淡入淡出排进同一条
时间线，套不进 `flipTo` 的单条补间）则在自己那条补间的 `onUpdate` 里调一次
`syncFlipFaces`，复用同一套硬切逻辑，不另写一份。
`flipTo` 在补间的 `onUpdate` 里每帧读 inner 当前的角度，
归一到 `[0, 360)` 后落在 `(90°, 270°)` 就把背面的 opacity 写成 1、正面写成 0，否则反过来。
硬切不做过渡：90° 时卡正好侧对观察者、投影宽度趋近于零，切换那一瞬间看不见。
判断读的是**元素当前的实际角度**而不是补间进度，所以翻过去和翻回来共用同一套逻辑，
`overwrite: 'auto'` 让新补间接管旧补间时也不用额外记状态。静止时的初始值（正面 1、背面 0）
写在 CSS 里，不靠 JS 首帧补。

之所以不用 `backface-visibility`，是因为 Chrome 实测它**在逐帧 JS 动画期间对合成层的朝向
判断不可靠**：静止时正确，一旦补间跑起来，转过 90° 之后正面并不消失，连同水平镜像一起
继续显示，直到补间结束那一刻才突然切成背面——"全程正面、结尾闪一下"。
卡面里那些被提成独立图层的子元素（`absolute` + `z-index` 的问号圆章、
`absolute` + `mix-blend-mode` 的高光层）逃出所在 face 的拍扁、翻面后镜像漏在另一面上，
也是同一族问题。逐个元素补一份 `backface-visibility` 补不完，而且补上之后动画途中的误判
还会和 opacity 打架造成闪烁，所以这些声明现在一条都不留。

**问号只长在技能牌上。** AI 牌正面已经把要看的都印全了，翻过去没有新东西，
所以对局手牌和卡组页的卡池卡 / 迷你卡都不给 AI 牌渲染问号，连背面整层一起省掉
（`HandFan` 和 `DeckScreen` 里各有一个 `flippable`）。
卡池里「即将上线」的技能牌同样不给（那一面只是一段还没生效的效果说明，
热区留着还会把"点卡面 = 弹一句即将上线"那一下吃掉），这一条只写在 `DeckScreen` 的 `flippable` 里。
AI 牌那张卡背（`ui/AiCardBack.tsx` 的技能详情）只剩两处还在画：卡组页放大查看时右边那张
伴随的背面大卡，以及对局里对手打出的牌飞到屏幕中央途中翻正的那一下。
看得见的那枚问号圆章是公共组件 `ui/CardHelpMark.tsx`（内联 SVG + 手绘抖动滤镜，
夜色圆底 + 米色线条，和卡角上另一颗圆钮 `.deck-circle` 同一副长相）：
用字符「?」画不了，整套界面的线条都挂着位移滤镜，作用在字体轮廓上会糊成一团。

**手牌右上角的问号：视觉和热区是两个元素**，因为两者对翻面的要求正好相反。

- 看得见的圆章（`.hand-fan__help-mark`）在翻转层**里**，正反两面各一个，
  倾斜和翻面都跟着卡一起转；正面那个放在 `.hand-fan__face--front` 里、`HandCardFace` 旁边，
  不放进 `HandCardFace`——那个组件被战场小卡复用，小卡没有翻面这回事，不该长出一个问号。
  背面那个放在 `.card-back` 里同样的位置，翻过去之后指针底下仍然压着一个问号，视觉是连续的。
  它们 `pointer-events: none`，不参与交互。
  两枚圆章（和同样分正反两份的 `.card-glare`）都不需要自己管朝向：
  该显示哪一面由所在 `.hand-fan__face` 的 opacity 决定，隐藏的那一面整层都是 0，漏不出来。
- 触发翻面的热区（`.hand-fan__help`）是一个**完全透明**的按钮，留在翻转层**外**、倾斜层里，
  位置尺寸都不动。热区绝对不能跟着翻面：跟着转的话，牌一翻到背面按钮就转到了指针够不着的
  地方，`pointerleave` 立刻把牌翻回正面，翻回来又被 hover 到，来回抖个没完。
  它靠倾斜层当绝对定位的基准，所以那一层的 `position` 不能去掉。
- **鼠标是移入翻过去、移出翻回来；触屏是点一下翻一次**（`handleHelpToggle`）。
  触屏的 `pointerenter` / `pointerleave` 其实是按下和抬手，照 hover 那套抄就成了
  "按住才看得见背面"，手一松就翻回去，字都没读完。热区在粗指针下还会放大到 32px 见方
  （看得见的问号圆章不动），指尖才按得中。

**命中几何只留 slot 和热区两处**：翻转层 `.hand-fan__inner` 整棵是 `pointer-events: none`，
卡面纯粹是画面。否则翻面途中 150px 宽的卡面绕 Y 轴扫出前后各 ±75px 的深度，中途会扫到热区
前面、在 `preserve-3d` 的三维命中测试里抢走指针：热区收到 `pointerleave` → 牌翻回去 →
卡面又扫回来触发 `pointerenter`，指针停着不动牌却自己来回翻。
这和 5.6 里 hover 放大要盖住原位是同一条原则——参与命中的形状不能在动画中途变形。

三个元素由 `applyLayout` 一起用 `autoAlpha` 淡入淡出（只有放大的那张牌才亮）。
必须一起，否则会出现"看得见问号却点不动"之类的错位；`autoAlpha` 归零时顺带关掉
`visibility`，没放大的手牌上那块热区也就不吃指针事件，指针扫过右上角不会误触发翻面。

高光是一层 `.card-glare`（正反两面各一层，正面在 `HandCardFace` 里，所以小卡自带），
`radial-gradient` 的圆心读 `--glare-x / --glare-y` 两个 CSS 变量（存的是指针的镜像位置，
见本节末尾），由 `gsap.quickSetter` 写在最外层上、靠继承传下去。混合模式用 `soft-light`：
卡面底色很深，`overlay` 在深色底上只是把原亮度翻一倍、仍然看不见。
卡面要 `isolation: isolate`，不然混合会拿卡背后的东西当底，高光溢出卡面。
渐变半径要写死（`circle 200px`），不写的话默认是 `farthest-corner`，
半径跟着指针到最远那个角的距离变，指针挪到卡角时反光会胀到两倍大。
半径比卡面对角线的一半（≈129px）大一截，指针挪到任何一角渐变都还没衰减完就出了卡面，
边缘不会被切出一道亮圈；代价是中间那道色标得压暗一点，否则整张卡会被提亮成一片。
背面那层直接沿用同一份 `--glare-x / --glare-y` 就行：`.hand-fan__face--back`
自带的 `rotateY(180deg)` 单看是镜像，但背面只有在 `.hand-fan__inner` 也转过 90° 之后
才显示，两个 180° 正好抵消。

**倾斜方向和高光位置是一套物理模型，改一边就得改另一边。**
倾斜是"指针在哪边、哪边就往屏幕里陷下去"，像用手指把卡牌那一角按住往下按——
反过来（指针那一角朝观察者抬起）也做过，用户实际体验后确认按下去这版手感更对。
高光跟着这个模型走，落在**指针的镜像位置**（对角）：被按下去那一角的对角翘向观察者、
正对光源，最亮的自然是它，而不是正往屏幕里陷的那一块。

`attachCardTilt` 必须在 `useGSAP` 的回调里调用：它把所有补间（`quickTo` 的内部补间、
归零补间）装在一个子 `gsap.context` 里，这个子 context 要挂到外层的 context 上，
卸载时才会被一起 revert。补间都在挂载那一刻建好，
指针回调里只给这些补间喂新值、不新建补间，所以那些回调不需要再包 `contextSafe`。
返回的 handle 有 `detach()`（摘监听 + 归零）
和 `reset()`（出牌时快速收手：出牌被拒绝的话卡还在原地，不主动归零它会僵在倾斜的样子）。

调用方（`HandFan` / `MatchStage`）都是**按元素增量挂/摘**，手牌或战场一变不能整批重挂：
`detach()` 会把倾斜和高光硬切回零，而指针很可能正停在一张没有离场的卡上，
它的倾斜会突然弹平、高光凭空消失，指针不动就不再有 `pointermove`，也就再也回不来。
另外依赖数组非空时 `useGSAP` 只在**卸载**时 revert，清理函数在依赖变化时不会跑，
所以离场元素必须在回调里自己摘掉，否则监听会一直留着。

### 5.8 屏幕中央的展示层

`.reveal-*` 那一族（遮罩 + 裁剪层 + 一张放大 1.7 倍的卡）由 `MatchStage` 的两条链路共用，
它们**严格互斥**——只有一张展示卡、一条呼吸浮动，同时跑就是两条 Flip 抢同一个元素：

- **强制展示**（对手出牌，不可打断）：收到对手的 `AI_DEPLOYED` / `SKILL_PLAYED`，
  在对手手牌里按 `data-flip-id` 找到那张牌当起飞点（正式对局是 `OpponentFan` 里的一张牌背，
  测试房是摊开的手牌条），遮罩淡入压暗，卡飞到屏幕中央——从倒扇形起飞的还要同时翻正
  （`flipTo` 从 180° 续转到 360°，同向续转不会半路掉头）——停 1.5 秒。
  之后 AI 牌从展示位接着飞到对方战场行并播上场特效；技能牌要么原地淡出（无目标），
  要么飞向被命中的那个格子并播命中特效（干扰类，`RevealTarget.hitId`）。
  后一段不用 Flip：目标格本来就在场上、也不会动，飞过去的那张卡是要消失的，普通补间更直白
  （`flyToTile`，位移写成相对量，免得起飞时被残留的浮动 transform 顶得跳一下）。
  `SKILL_PLAYED` 事件带的 `instanceId` / `targetInstanceId` 都只是给这里定位用的，
  引擎结算完全用不到它们。
- **放大查看**（玩家点战场小卡，敌我两行一视同仁）：格子留在原地隐藏占位
  （`.battle__tile--held`），展示层多渲染一份放大的副本；点遮罩（也就是点屏幕任意处）
  再飞回原格。整段不翻面，时长和层级全部复用上面那套，两条链路的手感才一致。
  互斥由 `revealBusyRef`（展示期间不给开查看）和 `abortInspect`（对手出牌时把查看直接掐掉，
  等不了飞回那 0.6 秒）两头保证。

放大查看还有第二份实现：`ui/CardZoomOverlay.tsx` 把"飞到中央 → 浮动 → 点遮罩飞回原位"
连同 `.reveal-*` 的时长、缓动、层级常量包成了通用组件，`/deck` 点开一张卡走的就是它。
它和 `MatchStage` 里那份是**各自独立的代码**，共用的只有这套类名和这批数值——
新对局流程刚落地，对局侧还没接进去，所以改任何一边的数值都要照着改另一边。
组件留了 `veilRef` 这个口子（把外部遮罩节点交给它补间），就是给将来对局侧接进来准备的：
同一页里两条链路必须补间**同一个**遮罩节点，各渲染一块的话交替时两块会同时半透明可见
（压暗和模糊翻倍），被抢占的那块更是没人再管，会永远停在全黑上吃掉所有点击。
理由和边界写在 `CardZoomOverlayProps.veilRef` 的注释里，动这块之前先看那里。
`/deck` 只有一条链路会动遮罩，所以不传 `veilRef`，用组件自带的那块就行。

我方自己打出的牌不走这一层：AI 牌直接从手牌 Flip 到战场（同样播上场特效），
技能牌在战场中央淡入亮相（`.battle__skill-show`）——自己打的什么牌不需要被强制看一遍。

几个绕不开的点：

- **事件回调在 React 提交新局面之前同步送达**（这也正是"那张牌此刻还在对手手牌 DOM 里"
  的原因），所以"是不是正在展示"只能读 ref 不能读 state（`revealBusyRef`、`inspectingRef`），
  同 `seatRef`。
- **展示遮罩（z-index 1100）压在特效层（80）之上**，所以展示期间收到的横幅先在
  `bannerQueueRef` 里排队，等遮罩淡出再补播——压在遮罩底下的横幅等于没播。
  两层全屏过场（抛硬币 / 回合结算）用的是同一个闸门机制。
- **和全屏过场同在 1100 那一档，靠让位而不是靠层级分胜负**：过场演着时 `startReveal`
  一律不受理；`QUESTION_REVEALED` 到达时先 `abortReveal` 把还没演完的展示收掉。
  这是因为"对手出完最后一张牌就结束出牌"时两条指令挨得极近，展示的 1.5 秒停留
  必然会和回合结算层撞上。
- **受理不了就降级，不排队**：展示层被占着（对手连着出牌）或找不到起飞点时，
  对方的 AI 牌退回一段简易的放大淡入（`popQueueRef`），技能牌则跳过这次展示。
  一次展示要两秒多，攒着挨个补播只会让画面越拖越远。
- **遮罩淡出 ≠ 演出结束，中间那一两秒要另有一把锁**：遮罩一开始淡出就不再吃指针事件了，
  而对手的牌还要从展示位飞 0.6 秒、再冒 0.8 秒烟，放大查看的飞回也还有 0.6 秒。
  这几段和我方出牌共用 `landing` 这一把演出锁（它同时喂 `HandFan` 的 `frozen`，见 5.6）。
  锁带编号（`landingTokenRef`）：解锁的回调常常延迟很久才跑，中间锁可能已经易主给下一次演出，
  对不上号就不放——比如联机时技能牌的兜底定时器先到点放了锁、玩家立刻又打出一张 AI 牌，
  迟到的技能展示时间线跑完时放掉的就会是别人的锁。
- **我方出牌的两条链路都要挂兜底解锁定时器**（`PLAY_LOCK_FALLBACK`）：它们的解锁都要等
  对面把新局面/事件送回来（AI 牌等新局面才有落点可飞，技能牌等 `SKILL_PLAYED` 才亮相），
  联机丢包、或者房主标签页被冻住而 socket 没断（`onPeerLeft` 也不触发）时那一步永远不来，
  锁就再没人放——手牌连 hover 抬牌都做不到，只能刷新页面。到点放锁后退回
  "出不了牌但还能抬起来看牌"（`disabled` 开着、`frozen` 关掉），是能忍的降级。
  演出真的起来了要**立刻把定时器撤掉**，否则往返慢一点就会被它在演出途中把手牌放开。
  对手出牌落场、放大查看飞回那两条链路的解锁全在本地驱动，不会卡住，不需要兜底。

### 5.9 存档

`src/save/save.ts` 是唯一碰持久化的地方，存在 localStorage 里：

```
key   ai-duel-save-v7
value { "ownedCards": ["..."], "wins": 3, "savedHero": "grace-hopper", "tutorialDone": true }
```

对外只有六个函数：

- `loadSave()` 读存档，任何一处读不通都回落到初始收藏；基础收藏始终开放，和额外解锁合并，不清空胜场。
- `recordWin()` 记一场胜利：胜场 +1，顺手用 `drawNewCard` 抽一张新卡再写回。
- `saveOwnedOrder(order)` 记下卡池的新排列。`ownedCards` 本来就是有序数组，组牌页把牌从牌组
  送回卡池时可以指定它落在哪一格，那一下之后的顺序就写回这里；顺序不影响任何玩法。
- `saveHero(hero)` 记下这次确认的英雄，下次进选英雄那一步时预填。
- `markTutorialDone()` 记下新手教程走完了（走到完成页、或中途点了「跳过教程」都会调）。
- `resetSave()` 清档回到新号。演示和调试用的，首页角落的 dev 区有入口。
  它只清这一个 key，牌组那份得另外调 `deckStore` 的 `resetDecks()`——首页那颗按钮两个一起调。

牌组不在这份存档里：玩家能存多套、还要能改名删除，那份数据自己一个 key，见 `save/deckStore.ts`。

几处约定：

- key 带版本号，结构要改就换下一个版本号：旧数据读不到自动当新号，不写迁移代码，
  老存档整份作废重来。v2 → v3 就是这么删掉 `tutorialDone` 的——教程下线，字段直接消失。
  v3 → v4 则是卡池整个换了一批（模型卡/提示卡 → AI 牌/技能牌），旧存档里的卡 id 一个都不剩。
  v4 → v5 是术语统一：卡 id 从 `agent-*` 改成 `ai-*`（`ai-gpt` / `ai-claude` /
  `ai-gemini` / `ai-deepseek`），存档里存的正是这批 id，所以老存档同样整份作废。
  v5 → v6 加了 `savedHero`（匹配后确认的英雄，下次进流程时预填）。
  v6 → v7 加了 `tutorialDone`（新手教程走完没有，首页「开始游戏」照它分流）。
  存的卡 id 全部来自当前卡池（AI 牌 + 技能牌两类）；英雄牌不进牌组也不进收藏，
  所以英雄只以 `savedHero` 这一个"选择结果"的形式存在。
- 读写全部包在 `try/catch` 里：隐私模式、禁用站点数据、配额占满时
  `localStorage` 本身就会抛异常，这时回落到初始收藏，游戏照常能玩，只是进度存不下来。
- 存档里残留的、已经从卡池里删掉的卡 id 会在读取时被丢弃，否则渲染时 `getCard` 会抛错。
  一张都不剩说明这份存档和当前卡池已经完全对不上，整份当新号处理。

## 7. 常用命令

```bash
pnpm install
pnpm typecheck          # 全仓类型检查
pnpm test               # 单元测试：core 规则、client 存档的读写与回落
pnpm dev                # 起客户端 (http://localhost:5173)
                        # 一个人调对局界面：首页 dev 区「测试对局」或匹配房「测试房（dev）」
                        # 端口被占时用 PORT=5174 pnpm dev
pnpm dev:server         # 起 Worker (http://localhost:8787)，同时发前端产物和 WebSocket
                        # 转发器的端到端测试：先 build 前端，再 pnpm --filter @ai-duel/server smoke
pnpm --filter @ai-duel/client build
```

**两台电脑联机**：客户端已经监听了局域网（`server.host = true`），
另一台用 `http://<你的局域网IP>:5173` 打开即可。
线上前端和转发器是同一个 Worker、同一个域名，联机地址默认就是当前页面的 origin，不用配。
本地开发是两个进程（Vite 在 5173、`wrangler dev` 在 8787），页面 origin 指不到转发器，
要在 `packages/client/.env.local` 里设 `VITE_SERVER_URL=http://<你的局域网IP>:8787` 指过去——
写 localhost 的话另一台电脑会连到它自己身上。
这么连是跨域的，靠 `/api/room` 响应上的 `Access-Control-Allow-Origin: *` 放行。

**静态部署**：路由用的是浏览器 history，直接把 `dist` 丢上静态托管需要配一条
「所有路径回退到 index.html」的重写规则，否则刷新 `/room` 会 404。
Vite 的 dev server 自带这个回退，开发时不用管。
